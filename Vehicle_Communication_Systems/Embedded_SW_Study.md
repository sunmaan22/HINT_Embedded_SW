## 1. 바이트에서 물리량까지

수신한 프레임은 채널·식별자·형식·길이·데이터·시각으로 이루어진 관측이다. 신호 의미를 얻으려면 해당 소프트웨어 버전에 맞는 통신 명세가 필요하다.

| 정보 | 확인 목적 |
|---|---|
| Start Bit·Length | 신호의 비트 위치와 폭 |
| Byte Order | 여러 바이트의 해석 순서 |
| Signedness | 부호 확장과 음수 해석 |
| Factor·Offset | 원시값에서 물리값으로 변환 |
| Unit·Range | 단위와 유효 범위 |
| Multiplexer | 같은 위치가 어떤 신호를 뜻하는지 결정 |
| 주기·갱신 조건 | 데이터 신선도 판단 |

기본 선형 환산은 `physical = raw × factor + offset`이다. 교육용 가정으로 두 바이트가 `34 12`이고 16비트 Little Endian이면 raw는 0x1234, 즉 4660이다. factor=0.5, offset=-10이면 물리값은 2320이다. 이는 실제 차량 신호 정의가 아니다.

수신 바이트 순서를 뒤집는 것만으로 모든 Big Endian DBC 신호를 처리할 수는 없다. 바이트 경계를 넘는 비트 필드는 데이터베이스의 시작 비트 규칙까지 따라야 한다.

## 2. 데이터베이스의 역할

| 형식 | 주로 설명하는 대상 |
|---|---|
| DBC | CAN 메시지·신호와 변환 |
| LDF | LIN 노드·프레임·신호·스케줄 |
| FIBEX | 네트워크 구조와 통신 정보 |
| ARXML | AUTOSAR 시스템·ECU·신호·PDU 구성 |
| ODX·PDX | 진단 서비스와 데이터 정의·패키지 |
| A2L | 측정·캘리브레이션 변수의 형식과 해석 |

파일이 열리는 것과 대상 ECU 버전에 맞는 것은 다르다. ID가 같아도 다른 버전에서는 비트 위치나 의미가 바뀔 수 있으므로 로그와 정의 파일의 버전을 함께 관리한다.

## 3. 시간·카운터·무결성

| 검사 | 발견하려는 문제 | 한계 |
|---|---|---|
| 링크 CRC | 전송 중 비트 손상 | 송신측 계산 오류까지 보증하지 않음 |
| 카운터 | 누락·중복·순서 변화 | 초기화·순환·허용 손실 정책 필요 |
| 타임아웃 | 정해진 시간 안에 갱신되지 않음 | 송신 중단 원인을 단독 확정하지 못함 |
| 범위 검사 | 허용 범위를 벗어난 값 | 범위 안의 잘못된 값은 통과 가능 |
| 일관성 검사 | 관련 신호 간 모순 | 신호별 측정·갱신 시각 차이 고려 |
| E2E 보호 | 종단 간 데이터 경로 오류 | 암호학적 인증과 별개 |

값과 함께 `유효 여부·마지막 갱신 시각·오류 상태`를 관리하는 관점이 중요하다. 타임아웃 후 이전 값을 계속 쓰는 정책과 값을 무효화하는 정책은 응용 요구사항에 따라 명시한다.

## 4. AUTOSAR 통신 모듈

| 모듈 | 핵심 책임 |
|---|---|
| COM | 응용 신호를 I-PDU로 구성·해석 |
| PduR | 설정된 PDU 경로에 따라 전달 |
| CanIf | 상위 계층과 CAN 드라이버 사이의 인터페이스 |
| CAN Driver | CAN 컨트롤러 접근과 전송·수신 처리 |
| CanTp | CAN 전송 메시지 분할·재조립 |
| DCM | 진단 통신과 서비스 처리 |
| DEM | 진단 이벤트·고장 상태 관리 |

일반 신호 통신은 COM 중심, 진단 메시지는 DCM·CanTp 중심으로 역할을 나누어 읽는다. DEM이 버스 프레임을 직접 디코딩하는 모듈이거나 DCM이 모든 센서 고장을 직접 판단하는 모듈이라고 이해하지 않는다.

전송 요청 성공, 컨트롤러 전송 완료, 수신 ECU의 데이터 수신과 응용 사용은 각각 다른 시점이다. 상태 변수와 콜백의 의미를 이 단계에 맞춰 구분한다.

## 5. 버퍼와 비동기 처리

| 경계 | 설계 질문 |
|---|---|
| ISR → 수신 처리 | 필요한 메타데이터가 함께 보존되는가 |
| 수신 큐 → 디코더 | 큐가 찼을 때 무엇을 버리는가 |
| 디코더 → 응용 | 값과 상태를 같은 시점의 묶음으로 읽는가 |
| 응용 → 송신 | 대기 중인 데이터의 수명은 충분한가 |
| 재조립 → 진단 | 길이·순서·시간 제한을 구분하는가 |
| 통신 → 로깅 | 저장 지연이 수신 처리에 영향을 주는가 |

큐 크기는 평균 트래픽뿐 아니라 순간 유입량과 최악 처리 지연에 영향을 받는다. 로그 누락이 버스 메시지 손실인지 로거 저장 실패인지 구분하려면 드롭 카운터·채널·시간 기준 등의 관측 정보가 필요하다.

## 6. 네트워크 관리와 대기 상태

| 기능 | 역할 |
|---|---|
| ComM | 기능의 통신 요구를 모아 모드 관리 |
| NmIf | 버스별 NM과 상위 기능 사이 연결 |
| 버스별 NM | 네트워크 활성·종료 협조 |
| Bus State Manager | 통신 장치와 스택의 상태 처리 |
| Partial Networking | 필요한 기능군의 활성 범위 관리 |

CAN NM의 Network Mode 안에는 Repeat Message, Normal Operation, Ready Sleep 등의 상태가 있다. Bus-Sleep과 Prepare Bus-Sleep은 별도의 모드로 구분한다. 단순한 일방향 순서가 아니라 로컬 요청·수신 이벤트·타이머·설정에 따라 전환된다.

링크가 연결되어 있어도 응용 통신 모드가 허용되지 않을 수 있다. 반대로 기능 하나가 통신 요구를 유지하면 다른 처리가 끝나도 절전 진입이 지연될 수 있다. 메시지 유무와 네트워크 사용 요구를 함께 이해한다.

## 7. 캘리브레이션 데이터의 의미

측정 로그의 ECU 내부 변수와 외부 CAN 신호는 같은 물리량을 다른 처리 단계에서 나타낼 수 있다. 필터 전후, 제어 주기와 통신 주기가 다르면 값이 즉시 같지 않을 수 있다.

| 구분 | 비교 시 필요한 조건 |
|---|---|
| 내부 변수와 버스 신호 | 단위·스케일·필터·갱신 주기 |
| 서로 다른 ECU 로그 | 시간 동기화와 전송 지연 |
| 기준 파라미터와 작업 파라미터 | 현재 사용 중인 데이터 버전 |
| A2L과 실행 이미지 | 변수 형식·주소·소프트웨어 버전 |

강의의 XCP·DAQ·페이지 개념은 이러한 측정과 파라미터 관리 구조를 이해하는 범위로 정리한다.

## 8. 진단 사례를 계층별로 읽기

다음은 첨부자료의 사례를 원인 분류 중심으로 재구성한 표이다. 증상 하나로 원인을 확정하는 표가 아니다.

| 관측 증상 | 가능한 원인 범주 | 함께 볼 정보 |
|---|---|---|
| 한 ECU의 데이터만 없음 | 전원·상태·필터·라우팅 | 다른 채널 수신과 ECU 상태 |
| Classic 프레임은 보이나 FD는 오류 | FD 형식·데이터 타이밍·지원 차이 | FDF·BRS·길이와 오류 기록 |
| 수신은 되지만 값이 이상함 | 정의 파일·엔디언·단위 | 원시 데이터와 버전 |
| 짧은 진단 메시지만 정상 | 전송 계층 흐름 제어·재조립 | 길이·순서·전송 상태 |
| 진단 응답이 거절됨 | 서비스 조건·세션·권한 | 응답의 서비스와 사유 |
| Ethernet 링크는 정상이나 서비스 없음 | IP·발견·구독·경로 | 서비스 정의와 상태 |
| 게이트웨이 전후 값이 다름 | 매핑·주기·필터·변환 | 양쪽 시각과 신호 정의 |
| 기록 파일에만 누락됨 | 로거 큐·저장 지연·필터 | 수신량·드롭·저장 상태 |
| 통신 종료가 늦음 | 남은 기능 요청·타이머 | 통신 요구와 NM 상태 |

응답 대기는 최종 실패와 다르고, 전송 계층의 확인은 진단 서비스 성공과 다르다. 통신 무결성이 정상이라는 이유만으로 응용 값의 정확성을 확정하지 않는다.
