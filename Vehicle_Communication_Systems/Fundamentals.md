## 1. 도메인별 통신 요구사항

차량 통신은 센서값, 제어 요구, 진단 정보와 대용량 데이터를 ECU 사이에 전달한다. 작은 메시지라도 전달 시점이 중요할 수 있고, 큰 데이터라도 제어 메시지보다 시간 여유가 클 수 있다.

| 영역 | 주로 전달하는 정보 | 설계의 중심 |
|---|---|---|
| 파워트레인 | 회전·토크·전원 상태 | 주기성과 응답 시간 |
| 섀시 | 운동 상태와 제어 요구 | 지연 한계·데이터 유효성 |
| 바디 | 버튼·조명·편의장치 상태 | 비용·배선·대기전력 |
| 인포테인먼트 | 음성·영상·사용자 정보 | 지속 처리량과 재생 품질 |
| ADAS | 센서 관측·인지 결과 | 대역폭·시간 정렬·데이터 신선도 |
| 외부 연결 | 원격 서비스·업데이트 데이터 | 연결 관리와 접근 통제 |
| 진단 | 상태·고장·서비스 응답 | 요청·응답 관계와 전송 완결성 |

같은 기능을 가진 ECU도 차량 구조에 따라 다른 버스를 사용할 수 있다. 도메인 이름만으로 프로토콜이나 허용 지연을 확정하지 않는다.

## 2. 분산형·도메인형·존형 구조

| 구조 | 묶는 기준 | 장점과 고려 사항 |
|---|---|---|
| 기능별 분산 | 개별 기능 | 기능 경계가 뚜렷하지만 ECU·배선 연결이 증가할 수 있다. |
| 도메인 집중 | 파워트레인·바디 등 기능군 | 기능군 내부 통합과 도메인 사이 연결이 중요하다. |
| 존 기반 | 차량 내 물리적 위치 | 가까운 입출력을 모으고 상위 컴퓨팅과 연결한다. |
| 중앙 컴퓨팅 연계 | 공통 연산·서비스 | 백본 대역폭·고장 격리·소프트웨어 배치가 중요하다. |

존 제어기와 중앙 컴퓨터는 같은 역할이 아니다. 존 제어기는 가까운 입출력·전원·통신을 연결할 수 있고, 중앙 컴퓨터는 여러 기능의 연산을 통합할 수 있다. 실제 차량은 여러 구조가 혼합될 수 있다.

## 3. 대역폭·지연·지터

| 항목 | 의미 |
|---|---|
| 링크 속도 | 링크에서 비트를 전달하는 속도 |
| 유효 처리량 | 응용 데이터가 실제 전달되는 양 |
| 전송시간 | 프레임을 선로에 내보내는 데 필요한 시간 |
| 종단 간 지연 | 생성된 정보가 수신측에서 사용 가능해질 때까지의 시간 |
| 지터 | 주기 또는 지연의 변동 |
| 결정성 | 명시한 조건에서 시간 동작을 예측·제한할 수 있는 성질 |

단일 속도 구간의 직렬화 시간은 `T = 전송 비트 수 / bit rate`로 계산한다. CAN FD처럼 구간별 속도가 다르면 각 구간의 시간을 합산해야 한다.

종단 간 지연에는 송신 태스크 대기, 큐·중재, 전송, 게이트웨이 처리, 수신 태스크 대기가 함께 들어간다. 링크 속도를 두 배로 높여도 전체 지연이 절반이 되는 것은 아니다.

압축 전 영상의 데이터율은 `가로 픽셀 × 세로 픽셀 × 초당 프레임 × 픽셀당 비트 수`로 추정한다. 해상도와 fps만으로는 충분하지 않으며 색 형식·압축·프레임 오버헤드를 별도로 구분한다.

주기 메시지의 단순 점유율 모델은 `U ≈ Σ(T_frame_i / period_i)`이다. 재전송·스터핑·비주기 트래픽과 우선순위 간 간섭은 추가로 고려해야 한다.

## 4. CAN의 구조와 중재

CAN은 메시지 식별자를 중심으로 여러 노드가 버스를 공유한다. 컨트롤러는 프레임·중재·오류 처리를, 트랜시버는 버스의 전기적 송수신을 담당한다.

| 요소 | 역할 |
|---|---|
| 식별자 | 메시지 구분과 중재에 사용 |
| 데이터 필드 | 상위 통신 명세가 정의한 정보 |
| CRC | 전송 무결성 검사 |
| ACK | 정상 수신한 노드의 확인 |
| 오류 상태 관리 | 반복 오류가 버스에 미치는 영향 제한 |

Classical CAN에는 11비트·29비트 식별자 형식이 있고 데이터 필드는 최대 8바이트이다. 식별자를 ECU의 물리 주소로 단정하지 않는다.

중재에서는 송신 비트와 버스 상태를 비교한다. Recessive를 보냈는데 Dominant를 관측한 노드는 중재에서 물러나고 우선한 프레임의 전송이 계속된다. 같은 형식의 데이터 프레임끼리는 작은 식별자가 일반적으로 우선하지만, 형식·제어 비트까지 포함한 중재 규칙을 고려해야 한다.

**ACK는 응용 기능의 처리 완료를 보증하지 않는다.** 특정 수신 ECU가 값을 적용했는지 확인하려면 응용 수준의 상태·응답을 따로 봐야 한다. 중재에서 물러나는 것도 통신 오류와 구분한다.

## 5. CAN FD와 CAN XL

CAN FD는 CAN의 중재 원리를 유지하면서 데이터 필드와 전송 방식을 확장한다.

| 항목 | Classical CAN | CAN FD |
|---|---|---|
| 식별자 | 11 또는 29비트 | 11 또는 29비트 |
| 최대 데이터 | 8바이트 | 64바이트 |
| 속도 | 프레임 내 기본적으로 동일 | BRS 사용 시 데이터 구간 전환 |
| Remote Frame | 존재 | 지원하지 않음 |
| 오류 검사 | 기존 CAN 규칙 | CRC·스터핑 규칙 확장 |

### DLC와 데이터 길이

| DLC | 데이터 바이트 |
|---|---|
| 0 ~ 8 | 0 ~ 8 |
| 9 | 12 |
| 10 | 16 |
| 11 | 20 |
| 12 | 24 |
| 13 | 32 |
| 14 | 48 |
| 15 | 64 |

DLC는 길이 코드이므로 CAN FD의 DLC 15를 15바이트로 읽으면 안 된다. 응용 데이터 길이와 프레임 데이터 길이가 다를 때는 패딩·상위 프로토콜의 길이 정의를 구분한다.

BRS는 비트율 전환 여부, ESI는 송신측 오류 상태를 나타낸다. CAN FD 지원 노드가 Classical CAN을 처리할 수 있다는 사실만으로 일반 Classical CAN 노드가 FD 프레임과 함께 동작할 수 있다고 가정하지 않는다.

CAN XL은 더 큰 페이로드 등을 다루는 별도의 확장이다. 강의는 최대 2048바이트 데이터를 소개한다. 이를 CAN FD의 설정값만 바꾸어 얻는 기능으로 이해하지 않는다.

## 6. LIN

LIN은 저비용·저속 입출력을 스케줄에 따라 연결하는 데 사용한다. Commander가 헤더를 시작하고, 해당 프레임의 Publisher가 응답 데이터를 제공한다. Publisher는 구성에 따라 Commander 노드의 응답 기능일 수도 있다.

| 구성 | 의미 |
|---|---|
| Break | 프레임 시작 구분 |
| Sync | 통신 타이밍 동기화 기준 |
| Protected Identifier | 프레임 식별 정보와 패리티 |
| Data | 신호 데이터 |
| Checksum | 응답 데이터 등의 무결성 검사 |
| Schedule Table | 어떤 프레임을 언제 시작할지 결정 |

스케줄은 전송 순서를 예측하기 쉽게 만들지만, 스케줄 주기가 길면 입력 변화가 전달되기까지 기다려야 한다. 이벤트 발생 시점과 다음 슬롯까지의 대기도 지연에 포함한다.

체크섬은 종류에 따라 PID 포함 여부가 다르고 진단 프레임 등에 예외가 있다. 모든 LIN 2.x 프레임에 같은 체크섬 계산을 적용한다고 단정하지 않는다.

## 7. FlexRay와 MOST

### FlexRay

FlexRay는 공통 시간 기준과 통신 사이클을 중심으로 구성한다.

| 요소 | 역할 |
|---|---|
| Static Segment | 정해진 슬롯의 시간 기반 전송 |
| Dynamic Segment | 미니슬롯 기반의 가변 전송 |
| Symbol Window | 특수 심벌 처리 |
| Network Idle Time | 사이클 내 여유와 시간 관련 처리 |
| 클럭 동기화 | 노드 간 시간 기준 보정 |
| 두 채널 | 구성에 따라 이중화 또는 트래픽 분산 |

프레임은 헤더·페이로드·트레일러로 구분하며 Frame ID, 길이, 사이클 정보와 오류 검사 필드가 해석에 사용된다. 두 채널을 같은 정보의 이중 전송에 쓰면 응용 처리량이 단순히 두 배가 되지 않는다.

### MOST

MOST는 멀티미디어 전송을 중심으로 발전한 네트워크이다. 시간 기준에 맞춘 스트림 전달과 제어 데이터가 함께 고려된다. 강의의 세대별 속도 표는 기술 구성을 비교하는 자료이며, 다른 프로토콜보다 모든 조건에서 우수하다는 의미는 아니다.

## 8. Automotive Ethernet·TSN·SOME/IP·DoIP

Automotive Ethernet은 차량용 물리계층을 사용하더라도 기본 Ethernet MAC 프레임 구조와 상위 네트워크 계층을 구분해 이해한다.

| 계층·기술 | 역할 |
|---|---|
| PHY | 매체에서 신호 송수신 |
| Ethernet MAC | MAC 주소·프레임·FCS |
| VLAN·우선순위 | 논리적 분리와 트래픽 분류 |
| IP | 네트워크 주소와 패킷 전달 |
| UDP·TCP | 상위 데이터 전송 방식 |
| SOME/IP | 서비스 기반 메시지 교환 |
| SOME/IP-SD | 서비스 제공·탐색·구독 관련 정보 |
| DoIP | IP 네트워크에서 진단 메시지 전달 |
| TSN | 시간 동기화·스케줄링 등 시간 민감 통신 기능군 |

MAC 프레임의 목적지·출발지 주소, 타입 또는 길이, 데이터와 FCS를 구분한다. 선로 전송의 프리앰블·SFD와 프레임 사이의 간격은 페이로드가 아니다.

Ethernet 링크 연결, IP 통신, 서비스 발견, 실제 응용 응답은 각각 다른 성공 조건이다. TSN 역시 하나의 기능을 켜기만 하면 모든 지연이 보장되는 기술로 이해하지 않는다. 경로·큐·스케줄·시간 동기화가 함께 맞아야 한다.

DoIP의 발견·상태 교환과 진단 데이터 전달은 사용하는 전송 경로가 다를 수 있다. DoIP의 전송 확인과 UDS 서비스 성공도 구분한다.

## 9. CAN Bit Timing

CAN의 한 비트는 여러 Time Quantum으로 구성된다.

`N_TQ = 1 + TSEG1 + TSEG2`

`T_TQ = 실제 분주비 / f_CAN`

`bit rate = f_CAN / (실제 분주비 × N_TQ)`

`Sample Point = (1 + TSEG1) / N_TQ × 100%`

| 요소 | 의미 |
|---|---|
| Sync Segment | 비트 동기화 기준 |
| TSEG1 | 샘플 시점 이전의 구간 |
| TSEG2 | 샘플 시점 이후의 구간 |
| SJW | 재동기화 시 조정 가능한 폭 |
| TDC | 빠른 FD 구간의 송신 루프 지연 보정 관련 기능 |

계산 연습으로 클럭 48 MHz, 실제 분주비 6, 전체 16 TQ를 가정하면 TQ는 125 ns, 한 비트는 2 μs, 비트율은 500 kbit/s이다. TSEG1=11, TSEG2=4라면 샘플 포인트는 75%이다. 이는 공식 확인용 가정이며 보드 권장 설정은 아니다.

계산한 시간 단위와 레지스터 인코딩은 다를 수 있다. CAN FD에서는 Nominal·Data 설정을 따로 구분한다. 비트율이 같아도 샘플 시점·클럭 오차·전파 지연 조건이 맞지 않을 수 있다.

## 10. 신호·진단·전송 서비스

| 기술 | 질문 | 주요 역할 |
|---|---|---|
| 일반 신호 통신 | 현재 값과 상태는 무엇인가 | 주기·이벤트 데이터 교환 |
| UDS | 어떤 진단 서비스를 수행하는가 | 요청·응답의 의미 정의 |
| CAN TP·ISO-TP | 긴 메시지를 어떻게 전달하는가 | 분할·재조립·흐름 제어 |
| AUTOSAR COM | 신호를 어떻게 PDU로 구성하는가 | 신호 패킹·언패킹과 통신 처리 |
| DoIP | IP 경로로 진단 데이터를 어떻게 전달하는가 | 진단 전송과 주소 관련 처리 |

CAN 링크가 정상이어도 전송 계층의 재조립이 실패할 수 있고, 재조립이 성공해도 진단 서비스가 거절될 수 있다. 계층마다 실패 의미가 다르다.

ISO-TP의 Single Frame, First Frame, Consecutive Frame, Flow Control은 각각 단일 전송·분할 시작·후속 데이터·수신측 흐름 제어를 나타낸다. Block Size와 STmin은 전송 흐름에 관여하며, UDS 서비스 응답 시간과 구분한다.

## 11. UDS·DTC와 응용 유효성

UDS는 진단 서비스의 요청과 응답 구조를 다룬다. 긍정 응답, 부정 응답, 응답 대기와 서비스별 상태를 구분해야 한다.

| 개념 | 해석 |
|---|---|
| 긍정 응답 | 요청 서비스의 응답 의미에 따라 성공 여부 해석 |
| 부정 응답 | 해당 요청과 거절 사유를 함께 전달 |
| Response Pending | 요청 처리 중이며 최종 결과가 아직 아님 |
| DTC | 정의된 진단 조건에 따라 기록된 고장 정보 |
| DTC 상태 | 현재·이력·확정 등 고장 판정의 진행 상태 |

DTC 하나만으로 고장 부품이 확정되는 것은 아니다. 발생 시점·조건·상태 정보와 연계해 해석한다.

링크 CRC가 정상이어도 송신측이 잘못 계산한 값이나 오래된 값을 보낼 수 있다. 카운터·시간 제한·범위·상호 일관성 검사는 전송 오류와 다른 종류의 문제를 확인한다. E2E 보호 또한 일반적인 암호학적 송신자 인증과 동일하지 않다.

## 12. 캘리브레이션과 네트워크 관리

캘리브레이션은 제어 프로그램의 파라미터와 측정값을 다루는 개발 개념이다. XCP는 측정·캘리브레이션 통신, A2L은 변수의 형식·주소·단위·변환 등 해석 정보를 담당한다.

| 개념 | 의미 |
|---|---|
| Polling 측정 | 도구가 값을 반복 요청 |
| DAQ | ECU 이벤트에 맞춰 설정된 변수 묶음 취득 |
| STIM | 시험 시스템에서 입력 데이터를 공급하는 개념 |
| 작업 페이지 | 실행·비교에 사용할 파라미터 데이터 구분 |
| 버전 일치 | 실행 소프트웨어와 변수 정의의 대응 |

네트워크 관리는 필요한 통신을 유지하면서 불필요한 활동을 줄이는 기능이다. ComM의 통신 요구 관리, 버스별 NM의 협조, Bus State Manager의 상태 처리를 구분한다. 부분 네트워킹은 필요한 기능군 중심으로 활성 범위를 관리하는 개념이다.

## 13. 게이트웨이와 라우팅

| 역할 | 처리 내용 |
|---|---|
| 전달 판단 | 입력 채널·식별 정보에 따라 목적지 선택 |
| 필터링 | 전달 정책과 수신 조건 적용 |
| 변환 | 신호·PDU·프로토콜 표현 사이의 매핑 |
| 큐잉 | 목적지 속도·우선순위에 맞춘 대기 |
| 상태 연계 | 목적지의 통신 가능 여부와 네트워크 요구 관리 |

게이트웨이는 선을 연결하는 장치만이 아니라 데이터 경계를 해석하는 소프트웨어 기능을 포함한다. 수신 프레임을 보존해 전달하는 방식과 신호를 꺼내 새 메시지로 구성하는 방식은 다르다.

라우팅 규칙에는 ID 외에도 채널·형식·길이·상태·목적지 정책이 필요할 수 있다. 중복 전달, 루프, 변환 단위 오류와 오래된 데이터의 재전송도 설계 대상이다.
