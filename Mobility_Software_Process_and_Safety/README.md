# Mobility Software Process and Safety

차량 전장·소프트웨어 개발이 **왜 프로세스와 기능안전을 요구하는지**, 그 요구를 **Automotive SPICE**와 **ISO 26262**가 각각 어떻게 규정하는지를 정리한 기술 노트이다. 자료의 원본은 3일 과정 교육자료이며, 여기서는 학습 일정·실습 안내를 제외하고 개념과 용어(KEYWORD) 중심으로 재구성했다.

[개발 프로세스 · A-SPICE](./Development_Process_and_ASPICE.md) · [기능안전 · ISO 26262](./Functional_Safety_ISO26262.md) · [전체 구성도](./Visual_Overview.md)

## 0. 이 문서가 다루는 범위

| 축 | 표준 | 무엇을 보장하는가 |
|---|---|---|
| 개발 프로세스의 능력 | **Automotive SPICE** (ISO/IEC 330xx 기반) | 요구사항·설계·구현·검증이 정해진 방식으로 수행되고 추적된다는 것 |
| 오작동으로 인한 위험 | **ISO 26262** (Functional Safety) | E/E 시스템의 **고장(malfunction)**이 수용 불가능한 위험으로 이어지지 않는다는 것 |
| 성능 한계로 인한 위험 | **ISO 21448** (SOTIF) | 고장이 없어도 **기능·성능 부족이나 오용**이 위험으로 이어지지 않는다는 것 |
| 악의적 위협 | **ISO/SAE 21434** (Cybersecurity) | 외부 위협과 그 사고 대응 체계로 인한 위험 |

네 표준은 경쟁 관계가 아니라 관점이 다른 층이다. 하나의 프로젝트에서 A-SPICE로 프로세스를, ISO 26262로 안전을, ISO 21434로 보안을 동시에 요구받는 경우가 많으며, 활동과 산출물은 상당 부분 공유된다.

## 1. 출발점 — 대규모 리콜 사례

전장·소프트웨어 결함이 어떻게 대량 리콜과 소송으로 이어지는지를 보여 주는 세 사례가 자료의 도입부를 이룬다.

| 사례 | 기술적 원인 (요지) | 결과 (요지) |
|---|---|---|
| **Takata 에어백** | 인플레이터 추진제(질산암모늄)가 습도·온도 반복에 열화 → 전개 시 금속 파편 비산 | 미국 등에서 약 3,400만 대 규모 리콜, 사망·부상 다수 |
| **GM 이그니션 스위치** | 디텐트 플런저·스프링의 토크 부족 + 무거운 키링 → 주행 중 스위치가 `ACC/OFF`로 이동 → 엔진 정지, 조향·제동 보조와 에어백 무력화 | 2005–2007 Cobalt / 2003–2007 Ion 등, 다수 사망(외부 분석 인용) |
| **Toyota ETCS 의도치 않은 가속** | 전자식 스로틀 제어의 페달/스로틀 위치 신호 A/D 변환 경로가 단일고장점(SPOF)일 가능성, 플로어매트·페달 문제 병존 | NHTSA·NASA 조사, SW 아키텍처 지적, 대규모 합의금 |

공통 교훈: **체계적 개발 프로세스 + 기능안전 + 추적성**이 없으면 소프트웨어·전자 결함의 원인 규명과 방어가 어렵다. "Root cause"는 비난이 아니라 조치의 방아쇠(trigger for action)로 쓰여야 한다.
