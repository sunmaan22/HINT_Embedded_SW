# Functional Safety — ISO 26262

**기능안전**은 차량 전자 시스템의 **오작동(malfunction)**으로 인한 사고 위험이 수용 가능한 수준으로 낮아진 상태다. ISO 26262는 이 상태를 달성하기 위한 **프로세스·개발 요구사항**을 제시하는 국제 표준이며, 이 노트는 그 용어·구조·핵심 활동을 정리한다.

[개론 · 리콜](./README.md) · [개발 프로세스 · A-SPICE](./Development_Process_and_ASPICE.md) · [전체 구성도](./Visual_Overview.md)

## 1. 안전을 보는 두 관점

| | Safety in use (제품 안전) | Functional safety (기능안전) |
|---|---|---|
| 문제 | 기능은 정상이나 설계 자체가 위험 | E/E 시스템의 **고장**이 위험 |
| 예 | 시트 히터 설계 온도 30–70℃ → 30–40℃로 변경 | 스로틀 신호 고장 → 의도치 않은 가속 |
| 접근 | 개발·운영 중 문제 인식 → 대책 | 오작동 × 운용 상황 조합의 **사전 위험 분석** → 안전목표·ASIL → 계층적 안전 요구사항 |

ISO 26262의 범위(scope)는 **E/E 시스템 오작동으로 인한 위험**이다. 감전·화재·연기·열·방사선·독성·인화성·부식·에너지 방출 같은 위험은 범위 밖(제품 안전 영역)이다.

- 정의: *"Absence of unreasonable risk due to hazards caused by malfunctioning behavior of E/E systems."* (ISO 26262-1)
- 위험(Risk)은 **위해의 발생 확률**과 **심각도**의 함수다. 확률은 노출(Exposure)·제어가능성(Controllability)·무결성(Integrity)에 좌우된다.
- 표준은 **수용 가능한 위험을 결정하는 표준화된 기법**을 제공한다: `잠재 위험 식별·평가 → ASIL ≥ A? → (아니오: 일반 개발) / (예: 위험을 수용 가능 수준으로 낮추는 추가 수단)` → 체계적 고장은 **회피·제거**(기능안전 관리 + 프로세스 개선), 랜덤 HW·체계적 고장은 **통제**(안전 메커니즘 개발).

## 2. 제정 배경

- 안전 관련 전장 시스템의 증가에 대응해 유럽 OEM·부품사 주도로 2011-11-15 제정. 9개국 19개 사 참여(BMW, VW, Toyota, GM, Volvo, Bosch 등).
- IEC 61508을 도메인별로 파생한 계열 중 자동차용: ISO 26262. (기계 IEC 62061, 공정 IEC 61511, 철도 EN 50128, 원자력 IEC 61513, 전력구동 IEC 61800-5-2 …)
- 효과: PL(제조물책임) 소송 시 ISO 26262 적용 여부에 따라 면책·경감 가능, 전자 제어 시스템의 안전 관련 품질 향상.
- OEM ↔ 협력업체: OEM은 업체 역량 평가·부품 ASIL 등급 요구·DIA 개발 관리·프로세스/제품 평가를 하고, 협력업체는 기능안전 프로세스 역량 입증·제품 적용·안전 증거 축적·제출을 한다.
- 판 이력: 1판 — 양산 승용차, 최대 총중량 3.5톤 미만. 2판 — E/E 안전 관련 시스템을 1개 이상 탑재한 양산 도로차량, 특수목적 차량 제외, 이륜차·트럭·버스 포함, 50 km/h 미만 모페드 제외.

## 4. 안전 생명주기 (Safety Lifecycle)

`3-5 아이템 정의 → 2-6 아이템 수준 영향 분석 → 3-6 HARA → 3-7 기능안전 컨셉` → (필요 시 타 기술 할당 / 외부 수단 / 제어가능성) → `4. 시스템 개발 {5. HW, 6. SW}` (병행: 2-6 확인 수단) → `2-6 생산 릴리스` → `7-5 계획 → 7-6 생산 → 7-7 운영·서비스·폐기`. 변경이 생기면 해당 생명주기 단계로 되돌아간다.

## 5. 핵심 용어 (ISO 26262-1)

### 인과 사슬 (Factors)

`Fault(비정상 조건) → Error(계산·관측값과 참·명세값의 불일치) → Failure(요구 기능 수행 능력의 종료) → Malfunctioning behavior(= failure 또는 의도치 않은 동작) → Hazard(위해의 잠재적 원천) + Operational Situation(노출 E, 제어가능성 C) → Hazardous event(hazard × 운용상황의 조합) → Harm(신체 상해·건강 손상; 심각도 S)`

- **fault (3.54)**: 엘리먼트 또는 아이템을 고장 나게 할 수 있는 비정상 조건. 영구·간헐·일시(특히 소프트 에러) 고장을 포함한다. 하위 시스템이 error 상태이면 상위 시스템의 fault가 될 수 있다.
- **systematic failure (3.164)**: 특정 원인과 결정론적으로 연결되어, 설계·제조공정·운영절차·문서 등의 변경으로만 제거되는 고장.
- **random hardware failure (3.118)**: 발생률을 합리적 정확도로 예측할 수 있는 물리적 HW 고장(SAE J1211, JEDEC JEP122의 PoF 방법론).
- **hazardous event (3.77)**: hazard와 operational situation(3.104)의 조합.
- **harm (3.74)**: 신체 상해 또는 사람 건강의 손상.
- **safety (3.132)**: 불합리한 위험(unreasonable risk, 3.176)의 부재.
- **vehicle function (3.178)**: 하나 이상의 아이템 구현으로 의도된, 고객이 관찰 가능한 차량 거동. 예: ACC는 서로 다른 ECU와 센서(레이더·라이다·카메라)로 구현될 수 있다.
- **architecture (3.1)**: 아이템/엘리먼트의 구조 표현으로 빌딩 블록·경계·인터페이스를 식별하게 하며, 요구사항의 블록 할당을 포함한다.
- **system (3.163)**: 최소한 센서·컨트롤러·액추에이터를 서로 관계시키는 컴포넌트/서브시스템의 집합. 센서·액추에이터는 시스템 내부일 수도 외부일 수도 있다.
- **component (3.21)**: 논리적·기술적으로 분리 가능하고 2개 이상의 HW 파트 또는 1개 이상의 SW 유닛으로 구성된 비-시스템 레벨 엘리먼트. 예: 마이크로컨트롤러.
- **element (3.41)**: 시스템, 컴포넌트(HW/SW), HW 파트, SW 유닛. SEooC일 수도 있다.
- **testing (3.169)**: 명세 요구사항 충족을 검증하고, 안전 이상(anomaly)을 검출하며, 요구사항이 주어진 맥락에 적합한지 확인(validate)하고, 거동에 대한 확신을 만들기 위해 아이템/엘리먼트를 계획·준비·운용하는 과정.
- **review (3.127)**: 작업산출물이 그 목표를 달성했는지 리뷰 목적에 따라 검사. 개발 단계 관점에서 verification review(3.181)와 confirmation review(3.24).

### 시간 간격 — FTTI

`결함으로 인한 오작동 → (오작동 지속) → 위험 사건`. 안전 메커니즘이 없을 때 결함에서 위험 사건까지가 **FTTI**(Fault Tolerant Time Interval).
- 안전 메커니즘이 있으면: `결함 검출 시간(진단 테스트 간격 포함) + 안전 상태 전환 시간(결함 반응 간격)` = **FHTI**(Fault Handling Time Interval) → 안전 상태.
- 비상 운영이 있으면 그 사이에 **EOTI**(Emergency Operation Time Interval)가 추가된다.

## 6. HARA와 ASIL

차량 오작동으로 인한 사고에 대해 위험을 평가하고, 방지·완화를 위한 **안전 목표**와 **ASIL**(Automotive Safety Integrity Level, 차량 무결성 수준)을 결정한다.

### 세 파라미터

| 심각도 S | 노출 확률 E | 제어가능성 C |
|---|---|---|
| S0 부상 없음 | E0 거의 불가능 | C0 일반적으로 제어 가능 |
| S1 가벼운·보통 부상 | E1 매우 낮은 확률 | C1 간단히 제어 가능 |
| S2 심각한 부상, 생존 가능 | E2 낮은 확률 | C2 보통의 경우 제어 가능 |
| S3 생존 불확실·치명적 | E3 중간 확률 / E4 높은 확률 | C3 제어 어렵거나 불가능 |

`S × E × C → QM / A / B / C / D`. **D가 가장 엄격**하고 A가 가장 낮다. **QM은 ASIL이 아니다**(일반 품질경영으로 충분). 대략 S1·E1·C 조합은 QM, S3·E4·C3은 D가 된다.

- **HARA (3.76)**: 아이템의 hazardous event를 식별·범주화하고, 관련 hazard의 방지·완화를 위한 안전 목표와 ASIL을 명세해 불합리한 위험을 피하는 방법.
- **ASIL (3.6)**: 불합리한 위험을 피하기 위해 적용해야 할 아이템/엘리먼트의 ISO 26262 요구사항과 **안전 수단(safety measures)**의 4개 수준 중 하나.
- **safety measures (3.141)**: 체계적 고장을 회피·통제하고 랜덤 HW 고장을 검출·통제하거나 그 해로운 영향을 완화하는 활동·기술 해법. (안전 메커니즘은 그 하위 집합)

### 예 — HARA 판정

경부고속도로, 100 km/h 주행 중 LKAS 오작동으로 차선 이탈·가드레일 측면 추돌, 동승자 1명 중상 가정 → E4 · S2 · C3 → **ASIL C**.

## 7. 안전 요구사항의 도출 (FSR → TSR → HW/SW)

하나의 hazard에서 계층적으로 안전 요구사항이 내려온다. 와이퍼/워셔 예:

| 단계 | 산출물 | 예시 문장 |
|---|---|---|
| 3-6 HARA | Hazard | (의도치 않은) 워셔 작동으로 운전자 전방 시야 방해 |
| 3-6 | **Safety Goal** | 워셔에 의한 시야 방해를 막을 것 (ASIL C) |
| 3-7 | **FSR / FSC** | 워셔가 3초 이상 작동하지 말아야 한다 (ASIL C) |
| 4-6 | **TSR / TSC** | 워셔 펌프가 3초 작동 시 와이퍼 제어기는 펌프를 Off 시켜야 한다 (ASIL C) |
| 5-6 | **HW 안전 컨셉/요구** | HW 엘리먼트 A는 펌프 작동 시간을 모니터링해 "pin N"으로 제어기에 전송 (ASIL C) |
| 6-6 | **SW 안전 컨셉/요구** | SW 컴포넌트 B는 "pin N" 신호를 처리해 "Pump=Off" 명령 전송 |

전 과정은 **8-6 안전 요구사항 명세 및 관리** 아래에서 추적·관리된다.

- **TSR** 명세는 ISO 26262-8:2018 Clause 6, FSC, 아이템의 시스템 아키텍처 설계와 일치해야 하고, 비안전 요구사항과 모순되지 않아야 하며, **안전 메커니즘**과 **안전 요구사항 달성에 영향을 주는 시스템의 자극-반응**을 명세한다. 외부 인터페이스·시스템 구성가능성·안전 관련 의존성과 제약을 고려한다.
- **TSC**는 TSR과 관련된 시스템 아키텍처 설계의 집합이다. TSC는 TSR을 포함하고, TSR은 시스템 아키텍처 설계 엘리먼트에 **할당(allocated to)**되어 구현(implement)된다.

## 8. 시스템 수준 개발 (Part 4)

### 엔지니어링·문서화 예 (과전압 검출)

- **(1) 시스템 요구사항 개발**: 안전요구사항 "의도치 않은 과도한 입력전압을 검출할 것" → FSR → 제어기 안전요구사항. SysRS: A 신호 오류 감지 / B ECU 오류 감지 / C Relay 오류 감지 / D 입력 전압 오류 감지. → 시스템 요구사항 명세서(기능 + 기술안전 요구사항).
- **(2) 시스템 설계**: SysDS — External Controller, ECU, Relay Control, Power Supply + Watch dog, Voltage monitoring. 시스템 안전분석(FMEA/FTA), 설계 검증. → 시스템 설계 명세서(운영 모드·아키텍처·기능안전 컨셉=요구사항 할당), 안전분석 결과서.

### 통합 3단계

1. 아이템을 구성하는 각 엘리먼트의 **HW와 SW 통합**.
2. 아이템을 구성하는 **엘리먼트 간 통합**.
3. 차량 내부 및 차량의 타 시스템과 **아이템 통합**.

## 9. HW 수준 개발 (Part 5)

`4.7 시스템 설계 → [5.5 착수 → 5.6 HW 안전요구 → 5.7 HW 설계 → {5.8 아키텍처 메트릭 평가, 5.9 랜덤 HW 고장 안전목표 위배 평가} → 5.10 HW 통합·테스트] → 4.8 아이템 통합·테스트` (+ 8.13 HW 컴포넌트 자격인정).

안전 활동: HW 안전요구(HSR) 개발·HSI 갱신 → HW 설계(아키텍처·상세) + 안전분석 → **FMEDA**(HAM & PMHF) → PCB 설계·조립 → HW 통합·검증.

### HW 아키텍처 메트릭

고장 분류: Safe faults / Latent multiple faults / Perceived multiple faults / **Single-point faults 또는 Residual faults**.

| 지표 | ASIL B | ASIL C | ASIL D |
|---|---|---|---|
| **SPFM** (단일점 고장 메트릭) | > 90% | > 97% | > 99% |
| **LFM** (잠재 고장 메트릭) | > 60% | > 80% | > 90% |
| **PMHF** (랜덤 HW 고장 확률 메트릭) | < 10⁻⁷/h | < 10⁻⁷/h (100 FIT) | < 10⁻⁸/h (10 FIT) |

### 고장 유형 (Freescale 안전 매뉴얼 인용)

| 유형 | 설명 |
|---|---|
| **SPF** Single-point Fault | 안전 메커니즘이 없는 엘리먼트의 고장 → 곧바로 잘못된 출력 |
| **LF** Latent Fault | 검출·인지되지 않은 고장, 출력은 아직 정상 → 두 번째 고장 전까지 숨어 있음 |
| **RF** Residual Fault | 안전 메커니즘이 커버하지 못한 고장 부분 → 잘못된 출력, 미검출 |
| **DPF** Dual-point Fault | 두 개의 잠재 고장이 겹쳐 → 잘못된 출력 |

### 확인 수단 (Confirmation measures, 2-6.4.9)

작업산출물(= 증거): 계획서(안전계획서, 통합·테스트 계획서), 엔지니어링 산출물(TSR, 시스템 설계, HSR, HW FMEDA 결과서, SSR, SW 아키텍처), Verification Report(Review/Test), 지원·관리 산출물(형상·변경관리 대장, 형상감사 보고서, QA 결과서, HW/SW 컴포넌트·SW 도구 인정 결과서, 역량/교육 현황).

- **Functional Safety Audit** (품질보증) → Process Safety Arguments
- 엔지니어링 산출물 → Product Safety Arguments
- 둘을 모아 **안전 케이스 보고서(Safety case report)** → **Functional Safety Assessment**의 입력.

| | Safety Case | Safety Case Report |
|---|---|---|
| 정의 | 안전 정당화의 총합 + 모든 뒷받침 자료(테스트·validation 결과서, 관련 설계 정보) | Safety Case의 핵심 요소를 요약하고 뒷받침 문서를 명확·간결하게 참조하는 문서 |

**안전 논거(Safety argument)**는 안전 생명주기 동안 작업산출물을 점진적으로 축적한 것으로, 프로젝트(계획·품질경영·형상관리) + 안전 확장(안전 목표·생명주기 활동·팀 책임·FMEDA 등 방법, V&V·평가·도구 자격인정, 안전 명세 산출물·베이스라인·영향 분석) + **안전 증거**(안전 목표·자격인정 보고서·HARA·안전 요구사항·안전 컨셉, V&V·평가·Proven-in-use 보고서, 안전 케이스 베이스라인·변경 추적성)로 구성된다.

## 12. 표준 통합 — A-SPICE + ISO 26262 + 21434 + SOTIF

- **ISO 26262**(고장으로 인한 위험)와 **ISO 21448 SOTIF**(고장 없는 성능 부족·오용으로 인한 위험)는 상호 보완한다. 인지 기반 ADAS/자율주행은 SOTIF 비중이 크다.
- **ISO/SAE 21434 Cybersecurity**는 악의적 위협과 사고 대응을 다루며, 위협 분석·리스크 평가(TARA)는 HARA와 구조가 유사하다.
- **A-SPICE**는 이 모든 것을 담는 개발 프로세스의 골격을 제공하고, 안전·보안 활동과 산출물은 대부분 A-SPICE 프로세스 안에서 수행·추적된다.

### 기능안전은 어떻게 달성되는가

| 개발 프로세스의 준수 | 안전 설계의 구현·검증 |
|---|---|
| 기존 V-모델 위에 안전 목표 달성을 위한 활동이 추가 정의됨. QA + Support/Management에 "safety" 결합 | 제품 아키텍처 위에 안전 기능 구현을 위한 **안전 메커니즘**이 추가 정의·통합됨. `안전목표 → 기능안전 요구사항 → 안전 메커니즘 → 안전목표` |

뒷받침: 기능안전 리뷰 · 기능안전 심사(Audit) · 기능안전 평가(Assessment).

### 사례로 보는 전체 흐름 — "P단 해제" 방지

- 안전목표(완성차): 의도치 않은 P단 해제로 인한 차량 이동을 방지해야 한다 (ASIL C).
- 안전요구사항(제어기 업체): 내부 결함으로 인한 "P단 체결 풀림"을 감지해야 한다 (ASIL C).
- **안전분석**(FTA): 체결 모터의 의도치 않은 동작 = 입력 전압 불안정 OR 외부 noise.
- **안전설계**: Shift Control Unit = MCU + SM1(아날로그 신호 모니터링) + SM2(운전자 경보).
- **안전성 검증**: FMEDA로 SPFM ≥ 97%, LFM ≥ 80%, PMHF < 100 FIT (ASIL C HW 아키텍처 메트릭) 확인 + **결함 주입(fault injection) 테스트**로 비정상 신호 인가 시 MCU 안전 기능 동작 확인.

> 절 번호·수치는 자료가 인용한 ISO 26262:2018 기준이며, ASIL 결정 표와 메트릭 목표치는 판·부록에 따라 세부가 달라질 수 있다.
