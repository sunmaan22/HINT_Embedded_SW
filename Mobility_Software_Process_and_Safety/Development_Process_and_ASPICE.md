# Development Process and Automotive SPICE

차량 E/E 시스템을 **정해진 방식으로 개발하고 그 근거를 남기는** 체계를 정리한다. 품질경영(IATF 16949) → 생명주기(V-모델) → 프로세스 능력(Automotive SPICE)의 세 층으로 쌓이며, 각 프로세스는 **입력 → 활동 → 검증 → 출력**과 추적성으로 기술된다.

## 1. 차량 전장 시스템의 계층 구조

E/E 개발은 큰 대상에서 작은 대상으로 분해(decomposition)했다가 다시 통합(integration)하는 구조다. 자료는 5단계로 나눈다.

| 계층 | 예 | 관심사 |
|---|---|---|
| Vehicle (차량) | 완성차 | 차량이 관찰 가능한 기능(vehicle function) |
| System (시스템) | Chassis · Powertrain · Body · Multimedia | 도메인 단위 기능과 안전 책임 |
| Sub-system | 변속기, 엔진, 모터 | 기계·전자 하위 조립 |
| E/E System | EMS, TMS, 인버터 | 제어 기능 / 시스템 통합 / 시스템 요소, 인터페이스 = 차량 네트워크 통신 |
| E/E System Element | 센서 · 컨트롤러 · 액추에이터 | HW·SW 통합 → 개별 Hardware, Software |

### 도메인별 특징

| 도메인 | 성격 | 대표 센서 | 대표 액추에이터·ECU |
|---|---|---|---|
| **Chassis** | 고장이 생명 위험으로 직결(ABS, EPS). **Safety Requirement** 적용. 운전자 조작부는 적고 센서·액추에이터가 많다 | 휠 속도, 보조배터리 전압, 브레이크 | 솔레노이드 밸브(전/후륜), 펌프·밸브 릴레이 |
| **Powertrain** | 동력 생성·전달. 동력원(엔진/모터/연료전지), 전달(클러치·변속기), 스타터·발전기 | 스로틀 위치, 흡입공기량(MAF), 흡기온, 엔진온, 노크, O2 | 점화플러그, 인젝터, 히터 / 엔진·모터·변속 ECU |
| **Body** | 편의 + 수동안전 2군. 편의(파워윈도, 선루프, 레인센서 와이퍼, 미러, 주차보조, 실내등, 시트), 수동안전(에어백, 시트벨트) | 각종 | 대부분 전동 모터 |
| **Multimedia** (인포테인먼트) | 내비, AVN, 통화, 음성인식, 인터넷. 대용량 데이터 → 네트워크 필요 | — | 통신: V2V/V2I/V2M, Bluetooth, WAVE. **보안(Secure)** 이슈 |

Chassis·Powertrain의 제어기가 만든 값(예: 휠 속도)은 계기판이나 다른 제어 기능에서도 재사용된다. 센서부터 액추에이터까지 모든 신호가 차량 네트워크를 거치는 것은 아니다.

## 2. 품질경영 표준의 지형

| | IATF 16949 | CMMI for DEV | Automotive SPICE | ISO 26262 |
|---|---|---|---|---|
| 내용 | ISO 9001에 자동차 요구 추가한 **QMS** | 개발 프로세스 베스트프랙티스(심사 = SCAMPI) | 개발 프로세스 베스트프랙티스 + **평가(assessment) 방법** | 안전 관련 시스템 개발 요구. IEC 61508의 자동차 적용 |
| 주관 | ISO | Carnegie Mellon SEI + CMMI Institute | HIS(OEM 이니셔티브) + Automotive SIG | ISO |
| 대상 | 시스템·부품 개발·양산 | SW·HW·기계 포함 시스템 엔지니어링 | SW 중심 시스템 개발 | 안전기능 전자(HW·SW) 시스템 개발 |
| 특징 | QMS 인증 | 성숙도 + 능력 | **능력(capability) 등급** | 제품 대상 Audit & Assessment, **ASIL 등급** |

### E/E 시스템 4대 국제 개발 표준

- **Automotive SPICE** — 개발 프로세스의 **능력**을 평가하는 모델. 엔지니어링 프로세스 품질을 입증한다.
- **ISO 26262 (Functional Safety)** — E/E 시스템 **오작동(고장)**으로 인한 사고 위험 최소화.
- **ISO 21448 (SOTIF)** — 고장이 없어도 **기능·성능 부족이나 예견 가능한 오용**으로 인한 위험 최소화.
- **ISO/SAE 21434 (Cybersecurity)** — 악의적 외부 위협과 사고 대응 체계로 인한 위험 최소화.

### 소프트웨어가 문제인 이유

자료가 인용하는 수치: 자동차 혁신의 약 72%가 소프트웨어에서 나오며, SW+HW의 생산원가 비중은 2000년 13%에서 2010년 35%로 올랐고, 고장 원인의 약 36%가 소프트웨어다. 그럼에도 SW 개발 프로세스는 HW보다 덜 형식화되고 "보이지 않는(invisible)" 상태로 다뤄져 왔다. A-SPICE·ISO 26262는 이 비대칭을 메우려는 시도다.

## 3. 생명주기와 V-모델

### 겹쳐 있는 여러 생명주기

차량 개발 생명주기는 여러 생명주기의 조합이다.

| 생명주기 | 단계 |
|---|---|
| Car L/C | Model Fix → Proto → Pilot → Mass Product |
| Product L/C | 개념설계 → 예비설계 → 상세설계·개발 → 생산 → 운용·지원 → 폐기 |
| Development L/C | V-모델 |
| Project L/C | 계획 → 실행(+감시·통제) → 종료 |

일반 프로젝트 생명주기(착수 → 조직화·준비 → 수행 → 종료)에서 시간이 갈수록 **리스크·불확실성과 변경 비용은 감소**하고, **비용·인력은 종 모양**을 그리며, **성공 확률은 증가**한다. 마일스톤 산출물: 프로젝트 헌장, 프로젝트 관리 계획서, 인수된 인도물, 아카이브된 프로젝트 문서.

### Automotive E/E V-모델 — 층을 쌓아 완성

자료는 V-모델을 다섯 겹으로 쌓아 설명한다.

1. **요구사항 주도 개발** — 고객 요구사항 →(계약/DIA)→ [요구사항 개발 → 설계 → 구현 → 통합·테스트] → 샘플/양산 릴리스 → 제품.
2. **+ 프로젝트 관리·지원** — 계획(일정·자원·프로세스) / 모니터링(진척·이슈) / 통제(조치·알람·에스컬레이션)가 개발을 감싼다. 좌측 개발과 우측 검증이 짝을 이루고 그 사이에 검증 리뷰가 있다(점선 = 만족, 실선 = 검증). 지원: 형상/변경 관리, 문제점 관리, 생산·공정 관리.
3. **+ 안전분석** — 안전 계획/모니터링/통제 추가. `안전목표 → 안전 요구사항 → 안전 컨셉 → 안전 메커니즘`. 안전분석 = FMEA·FTA·DFA. 제품 측 특별특성 `Cpk ≥ 1.67`. 하단에 DIA(협력업체 기능안전 역량평가·선정), HW 엘리먼트·SW 컴포넌트 평가·자격인정·재사용, **SW 도구 신뢰수준(TCL) 평가·인정**, 사용 입증(Proven in Use) 추가.
4. **+ 확인 수단(Confirmation measures)** — 기능안전 심사(Audit: ISO 26262 프로세스대로 개발됐는가) / 기능안전 평가(Assessment: 완성차 레벨에서 기능안전이 달성됐는가, 심사 포함).
5. **+ ISO 26262 시스템/HW/SW V** — 시스템 V(… → 시스템/아이템 통합 테스트[HW-SW·시스템·차량 통합] → 안전성 확인 테스트) + HW V(HW 요구사항 → 설계 → 아키텍처 메트릭 평가 → 우발고장 안전목표 위배 평가 → 구현 → 통합·테스트) + SW V(SW 요구사항 → 아키텍처 → 단위 설계 → 구현 → 단위 검증 → 통합·검증 → 임베디드 SW 테스트).

### 프로세스의 구성 요소

하나의 프로세스(태스크)는 ETVX 형태로 기술된다: **목적, 입력, 진입 기준(Entry), 활동, 역할, 척도, 검증 단계, 출력, 종료 기준(Exit)**. 태스크는 방법·체크리스트·교육자료·도구·QA의 지원을 받는다. 표준 프로세스는 테일러링 가이드라인을 거쳐 프로젝트별 **정의된 프로세스(defined process)**가 된다. 제품 개발은 재현 가능한 엔지니어링이어야 하며 예술(art)이 아니다.

## 4. CMMI가 말하는 성숙한 조직

프로세스 = "입력을 출력으로 변환하는 상호 연관된 활동의 집합"(ISO 9000, ISO/IEC 12207/15288).

| 미성숙 조직 | 성숙 조직 |
|---|---|
| 즉흥적·반응적, 일정 압박에 품질 희생, 객관적 데이터 없음 | 조직 수준 프로세스 능력, 계획된 작업, 품질 모니터링, 과거 실적에 근거한 추정 |

### 프로세스 영역 묶음

- **기본 프로젝트 관리**: PP(계획), PMC(감시·통제), REQM(요구사항 관리), SAM(공급자 협약 관리)
- **엔지니어링**: RD(요구사항 개발), TS(기술 솔루션), PI(제품 통합), VER(검증), VAL(확인)
- **지원**: CM(형상관리), MA(측정·분석), PPQA(프로세스·제품 품질보증)
- **OPA(조직 프로세스 자산)**: 계획·프로세스·절차·지식베이스, 교훈(lessons learned)과 이력 정보. 프로젝트 착수 시 OPA의 추정치·절차를 쓰고, 종료 시 실적과 개선점을 되돌려 준다.

성숙도가 오르면 추정 오차 범위가 좁아지고(예: L1–2의 +20/−145% → L3의 ±20%), 출시 후 결함이 줄며, 일정 예측 정확도와 재사용률이 올라간다는 사례(Boeing)를 자료가 인용한다.

## 5. Automotive SPICE

**SPICE** = *Software Process Improvement and Capability dEtermination*. ISO/IEC 15504(정보기술 — 프로세스 평가)의 자동차 버전으로, E/E 시스템 개발 프로세스의 품질 수준을 평가하는 모델이다. ISO/IEC 15504 + ISO/IEC 12207을 토대로 하며 **VDA**가 PAM(Process Assessment Model)을 발행한다.

- 목적: OEM이 협력업체(ECU 공급사)의 개발·품질경영 능력을 평가한다. 한 번의 평가 결과를 여러 OEM에 제출할 수 있다.
- **HIS** = Herstellerinitiative Software(OEM 이니셔티브). **Automotive SIG** = The Procurement Forum + The SPICE User Group의 공동 SIG. 참여: AUDI, BMW, Daimler, Fiat, Ford Werke, Jaguar, Land Rover, Porsche, VW, Volvo.
- **ISO/IEC 330xx** (15504 대체): 33001 개념·용어 / 33002 평가 요구 · 33003 측정 프레임워크 요구 · 33004 프로세스 모델 요구 / 33010 평가 가이드 · 33014 개선 가이드 · 33016 PA Body of Knowledge / 33020 측정 프레임워크.

### 프로세스 그룹

ACQ(획득) · SPL(공급) · **Engineering(SYS/SWE/HWE/MLE)** · SUP(지원) · MAN(관리) · PIM(프로세스 개선) · REU(재사용). v4.0에서 단일 ENG 그룹이 SYS + SWE + **HWE(신규)** + **MLE(신규)**로 분리됐다.

### 능력 차원 — ISO/IEC 33020

평가 모델 = **프로세스 차원**(PRM: 목적·성과) × **능력 차원**(능력 수준·프로세스 속성·평정).

- 평정 척도 **N / P / L / F**. 각 속성이 아래 수준에서 모두 **F**여야 다음 수준의 대상 속성을 **L 또는 F**로 볼 수 있다.

| 수준 | 필요 조건 |
|---|---|
| CL1 Performed | PA1.1 = L/F |
| CL2 Managed | PA1.1 = F; PA2.1(성과관리)·PA2.2(작업산출물 관리) = L/F |
| CL3 Established | ~PA2.2 = F; PA3.1(프로세스 정의)·PA3.2(프로세스 전개) = L/F |
| CL4 Predictable | ~PA3.2 = F; PA4.1(정량 분석)·PA4.2(정량 통제) = L/F |
| CL5 Innovating | ~PA4.2 = F; PA5.1·PA5.2(프로세스 혁신) = L/F |

- **성과 지표** = 기본 프랙티스(BP) + 출력 정보 항목(II).
- **PA2.1 / GP2.1.1** — 정량적 성과 목표 식별(프로세스 요구에서 도출), 범위 정의, 제약 고려. 4대 성과 목표: 적기 산출(품질 기준 충족 산출물), 사이클 타임·빈도, 자원 사용, 경계. **타협 불가 최소 목표: 자원·공수·일정.**
- **GP2.1.x**: 목표·전략 식별 → 계획 → 계획 대비 모니터링 → 조정 → 권한·책임 정의 → 자원 확보 → 관계자 간 인터페이스 관리. **GP2.2.x**: 작업산출물 요구 정의 → 문서화·통제 요구 정의 → 식별·문서화·통제 → 검토·조정.
- **Level 3 제네릭 프랙티스** — PA3.1: 표준 프로세스 수립·유지(요소·순서·템플릿·테일러링 가이드), 필요 역량 결정, 필요 자원 결정(HIL/SIL 시뮬레이터, 도구 라이선스 등), 표준 프로세스 모니터링 방법 결정(감사·품질평가). PA3.2: 정의된 프로세스 전개(공식 테일러링 절차), 역량 확보(격차 → 특별 교육), 자원·인프라 확보(ALM/PLM), 정의된 프로세스 성과 모니터링 → 정량 데이터를 전사 라이브러리로 피드백.

### 예 — SWE.1 SW 요구사항 분석

기본 프랙티스: SW 요구사항 명세 → 구조화 → 분석 → 운영환경 영향 분석 → 검증 기준 개발 → 양방향 추적성 수립 → 일관성 확보 → 합의된 SW 요구사항 전달. 출력: 요구사항 명세서, 인터페이스 요구사항 명세서, 검증 기준, 추적 매트릭스, 검토·변경·의사소통 기록.

## 6. 프로젝트 관리 — MAN.3와 PMBOK

### MAN.3

합의된 고객 요구사항 분석에서 **Feature 목록**(고객 인도 대상 시스템 기능)을 도출하고, 어떤 Feature를 A/B/C/D-Sample에 인도할지 **릴리스 계획**을 세운다. 프로젝트 단계는 A-Sample → B-Sample → C-Sample → SOP이며 SUP.9(문제해결)·SUP.10(변경요청)·SUP.8(형상)·MAN.3(PM)·SUP.1(QA)이 이를 감싼다. 샘플마다 System + HW + SW의 "W"가 돌고, HW FIX / SW FIX와 생산 툴링·라인 셋업이 SOP를 향해 진행된다.

### WBS와 일정(Schedule)

| | WBS | Schedule |
|---|---|---|
| 정의하는 것 | **무엇을** 인도하는가 / 범위 | **어떻게·언제** 수행하는가 |
| 지향 | 인도물 | 태스크·활동 |
| 명명 | 명사·형용사 | 동사 |
| 작성 | PM + 이해관계자 | 프로젝트 스케줄러 |
| 순서 | 없음 | 있음 (WBS 먼저, 일정 나중) |
| 기준선 | 범위 기준선 | 일정 기준선 |
| 지식 영역 | 범위 관리 (착수/계획) | 시간 관리 (계획) |

`작업 → 작업 패키지(ID·제목·추정 공수, WBS 최하위) → 활동 → 일정 태스크(기간·시작/종료·담당)`. 총 공수 = 작업 패키지별 공수의 합.

**임계경로법(CPM)**: WBS 작성 → 활동 정의 → (활동자원·기간 산정, 활동순서 배열) → 일정 개발 → 예산 결정. 노드는 ES/기간/EF, LS/여유/LF로 표기하고, 여유(float) 0의 연쇄가 임계경로다. **3점 추정 + PERT**: 기대값 = (낙관 + 4×최빈 + 비관) / 6.

**감시·통제**는 상태·일정·비용(계획 대비 실적)·자원·정산·품질(QA 활동)·변경·목표원가·투자를 한 화면에서 본다.

### PMBOK

PMI 발간. 프로젝트 관리 = "요구사항을 충족하도록 프로젝트 활동에 지식·기술·도구·기법을 적용하는 것"이며, 조직이 프로젝트를 **효과적·효율적으로** 수행하게 한다.

| | 6판 | 7판 |
|---|---|---|
| 골격 | 지식 영역(통합·범위·일정·원가·품질·자원·의사소통·리스크·조달·이해관계자) + 프로세스 그룹(착수·계획·실행·감시통제·종료) | 가치 전달 시스템 + **12 원칙** + **8 성과 영역** + 테일러링 |
| 12 원칙 | — | 관리(Stewardship), 팀, 이해관계자, 가치, 시스템 사고, 리더십, 테일러링, 품질, 복잡성, 리스크, 적응성·회복력, 변화 |
| 8 성과 영역 | — | 이해관계자, 팀, 개발 접근·생명주기, 계획, 프로젝트 작업, 인도, 측정, 불확실성 |

프로젝트 선정은 규제·법·사회 요구, 이해관계자 요구, 제품·프로세스·서비스 생성/개선/수정, 비즈니스·기술 전략 구현/변경 중 하나 이상에서 비롯된다. `PMIstandards+`는 추정·일정·WBS·요구사항 관리 등 실무 가이드에 대한 디지털 접근을 제공한다.

## 7. 엔지니어링 프로세스 — SYS / SWE

각 프로세스는 **입력 산출물 · 참여 인원 · 관련 표준 · 수행 내용(활동) · 출력 산출물 · 관련 도구**로 기술된다.

### SYS.1,2 — 시스템 요구사항 분석·명세

- 입력: 고객 제어 사양서, 고객 기능안전 요구사양, 아이템/시스템 정의(운영·동작 모드, 예비 아키텍처 + 외부 인터페이스), 안전목표.
- 활동 1 **고객 요구사항 분석**: 요구사항별로 `기술 난이도 × 비용/리소스 × 프로젝트 리스크`를 판정하고 대책을 세운다.
- 활동 2 **시스템 요구사항 명세·검증 리뷰**: 제어 기능 + 안전 기능을 만족하는 시스템 레벨 명세서를 작성(추적관리 포함)하고 체크리스트로 검증 리뷰.
- 명세 순서(level of details 준수): `Context diagram → External interface → Mode & State → 기능 요구사항 → 비기능 요구사항`.
- 출력: 시스템 요구사항 명세서, 검증 리뷰 결과서, 요구사항 추적 매트릭스.

**요구사항 분석의 두 관점**: ① 작성된 요구사항 자체 — 정확성·구현가능성·검증가능성. ② 프로젝트에 미치는 영향 — 일정·비용·기술난이도 → **프로젝트 위험** → MAN.5 위험관리 프로세스로 연결.

### SYS.3 — 시스템 아키텍처 설계

순서: `Internal block diagram → Internal element 정의 → Internal interface 정의 → Dynamic behavior 설명 → 설계 대안·제약`. Internal interface에서는 기술적 방식뿐 아니라 **어떤 "정보"를 주고받는지**를 명확히 정의하며, 이것이 HSI(HW-SW 인터페이스) 작성의 기초가 된다.

### SWE.2 — SW 아키텍처 설계

- 활동 1 **아키텍처 설계**: SW 컴포넌트/단위와 내·외부 인터페이스 정의·배치, 추적관리, 검증 리뷰. 산출물 = SW 정적 아키텍처 + SW 동적 설계.
- 활동 2 **SW 안전분석**: SW 고장이 차량 레벨 고장으로 가는 것을 막기 위해 **FMEA + FTA**를 수행하고 요구사항·아키텍처를 갱신. FMEA → 안전 관련 고장 식별, FTA → 고장 원인 분석·안전 메커니즘 수립.
- 도구 예: IBM Rhapsody, Polarion, APIS IQ-SW(FMEA), RWB(FTA).

### SYS.4,5 / SWE.4,5,6 — 통합·자격 테스트

- 활동 1 **테스트 케이스 개발**: 사양·구현을 단계적으로 검증하도록 단위/통합/자격 절차를 계획하고, 사양(요구사항·아키텍처·단위 설계) 기준으로 케이스를 작성. 특정 도구에 따라 형태가 달라질 수 있다.
- 활동 2 **결함 관리**: `결과 보고 → 결함 등록 → 조치 계획·이행 → 조치 결과 검증 → 결함 종료`, 회귀 테스트 루프 포함.

### 플러그인 개념

최상위는 시스템 "V"로 조직된 모든 시스템 엔지니어링 프로세스다(A-SPICE PRM/PAM 3.1, D.1). ECU는 `ECU(SYS.x) → SW → {Algorithms(SWE.x), Data model(MLE.x)}, HW(HWE.x), Housing`으로 분해되고, 메카트로닉 시스템은 `Vehicle → Mechatronic system(SYS.x) → Drive/Power pack → Motor + ECU, Mechanical`로 확장된다. 트리에서 2개 이상 엘리먼트로 구성되면 컴포넌트, 더 분해할 수 없거나 공급업체가 개발하면 블랙박스 엘리먼트다.

## 8. 지원 프로세스

### SUP.1 품질보증

QA는 **설계 품질**과 **양산 품질**을 구분한다(이 과정은 설계 품질). 품질보증 전략보다 **품질 목표**가 먼저 있어야 한다. 예: "샘플 납품 후 결함 OO개 미만" → 파생 지표: 기능안전 요구사항 커버리지 100% 유지, 작업산출물 검토(verification review) 80% 이상 수행, 변경·결함 조치 지연율 20% 미만.

| 구성적 QA (Preventive) | 분석적 QA (Retrospective) |
|---|---|
| 조직 표준 프로세스 수립·내재화, 표준 전산 환경 운영, 교육·코칭 | **V&V**(verification review = walkthrough·inspection, 시뮬레이션, 프로토타이핑, 테스팅) + **품질 감사**(인터뷰, 작업산출물 검토, confirmation review, functional safety audit) |

### SUP.8 형상관리

형상(configuration)은 제품을 센서/프로세서/액추에이터로 분해하고 각 항목에 컴포넌트 정보(Model No., Part No., Revision)와 소프트웨어 정보(SW ROM No., Program Std., Data Std.)를 붙인 것이다. **형상항목(CI)**은 전체 개발 생명주기에서 무결성(integrity)을 유지해야 한다. 각 단계에서 스냅샷을 찍어 베이스라인(요구사항 → function baseline, 생산 → product baseline)을 만들고, 변경 요청/오더로 갱신한다.

### SUP.9 문제해결관리

결함은 품질감사·형상감사·확인 수단(기능안전 리뷰/심사/평가)·검토·정적/동적 분석·측정(MA) 등에서 나온다. `Defect → 문제점/결함관리 프로세스`, `고객 요청 → 변경관리 프로세스 ← CCB`. **허용범위 초과**(품질목표·성과모델·개발사양 대비)이거나 일정 지연·자원 문제·기술난이도·품질 문제가 크면 **이슈관리 프로세스**로 승격한다.

### SUP.10 변경요청관리

스윔레인: `변경 요청자 → 변경 관리자(요청서 작성 → 심의 → CCB 소집? → 심의 결과 → 수용?) → 상위관리자/CCB → (반려/연기 | 변경 담당자: 계획 수립 → 적용·검증 → 형상관리 → 결과 통보)`.
CR 상태: `opened → reviewed → assigned → implemented → closed` (그 외 rejected / postponed).

## 9. 추적성(Traceability)과 일관성(Consistency)

| 종류 | 대상 | 목적 |
|---|---|---|
| **수평 추적성** | 서로 관련된 컴포넌트 간 기능(인터페이스·데이터) | 효과적 통합 테스트·문제 해결·구현 |
| **수직 추적성** | 요구사항 ↔ 아키텍처·상세설계·코드·단위/통합/시스템 테스트 (양방향) | 변경 영향 파악, 커버리지 확인 |
| **이슈·버그·변경 추적** | 변경 프로세스와 그 생명주기 산출물 | 형상·통합·릴리스 식별 |

예: `SYS_FS_REQ_143`(ESC는 Yaw Rate가 상수 A 이상일 때 Stand-by 전환)에서 상수 A를 A'로 바꾸면, 하위 `SW_FS_REQ_95A` → `SDS_Mod_47`(설계) → `TransitionStandby()` 코드 → 테스트 케이스까지 변경이 전파돼야 한다. 하나의 상수 변경이 요구사항–설계–코드–테스트를 관통한다.

**일관성**은 지원 프로세스로 보장된다: 각 작업산출물을 버전 관리해 형상 저장소에 넣고(형상 관리), 요구사항·설계·구현·테스트에 대한 검증 활동과 결함 관리를 붙이며, 변경 요청은 검토를 거쳐 변경·결함 저장소로 이어진다. 활동 결과는 기록·추적된다.

> 표의 프로세스 관계는 논리적 기능 관계다. SYS/SWE의 각 프로세스가 별도 ECU나 별도 조직을 뜻하지는 않으며, 구현에 따라 통합 수준이 달라진다.
