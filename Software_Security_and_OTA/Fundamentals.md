## 1. OTA 기본 모델과 공격 표면 (PART 01)

OTA는 무선 전달 경로로 소프트웨어를 원격 갱신하는 절차다. 배포 주체, 전달 경로, 수신 주체, 설치 대상의 네 역할을 나누어 본다. 다운로드·기록·재시작만 구현하면 받은 바이트가 그대로 실행 후보가 된다.

| 공격 지점 | 조작 | 필요한 판정 |
|---|---|---|
| 전송 경로 | 이미지 변경 | 인증된 기준값과 해시 비교 |
| 배포 저장소 | 배포 파일 교체 | 배포물 서명·서명자 권한 |
| 연결 상대 | 가짜 서버 | TLS 경로·이름 검증 |
| 과거 배포물 | 정품 구버전 재전송 | 보안 버전 하한·최신성 정책 |
| 단말 검증 기준 | 공개키·신뢰 목록·하한 변경 | 기준과 검증 코드의 보호 |
| 설치 후 저장 | 검증 이후 이미지 변경 | 기록 후 재검사·부팅 시 검증 |

이는 강의의 여섯 지점을 정리한 표이며 모든 위협의 완전한 분류는 아니다. 소개된 과거 차량 공격 사례도 OTA만의 단일 원인으로 일반화하지 않는다.

## 2. 해시와 기준값의 신뢰 (PART 02)

SHA-256은 임의 길이 바이트열을 256비트, 즉 32바이트의 값으로 변환한다. 16진수로 표시하면 64자리다. 동일 입력은 동일 출력이지만, 해시에는 키가 없어 누구나 계산할 수 있다.

| 성질 | 주어진 것 | 찾기 어려워야 하는 것 |
|---|---|---|
| 역상 저항성 | 해시 `h` | `H(m)=h`인 입력 |
| 제2역상 저항성 | 특정 입력 `m` | 같은 해시를 갖는 다른 입력 |
| 충돌 저항성 | 정해진 입력 없음 | 해시가 같은 서로 다른 입력 쌍 |

이상적인 256비트 해시의 일반 공격 비용 규모는 역상·제2역상 약 `2^256`, 충돌 약 `2^128`이다. 이것을 개별 구현의 실험적 증명이나 모든 입력 조건에 대한 보증으로 읽지 않는다.

작은 예제의 인덱스 14를 `0x30 → 0x31`로 바꾸면 입력은 1비트만 달라진다. 해시의 많은 비트가 바뀌는 눈사태 효과를 관찰할 수 있지만, 한 번의 관찰은 암호학적 안전성 증명이 아니다.

```text
파일만 변경:       H(m') != h_ref        → 거부
파일 + 기준 변경: H(m') == H(m')         → 비교 통과
```

두 번째 경우는 해시 충돌이 아니다. 공격자가 기준값도 바꾸었기 때문에 비교가 성립한 것이다. **해시 비교의 보안 근거는 기준 해시의 인증과 보호에 달려 있다.**

## 3. HMAC과 공유키 유출 (PART 03~04)

HMAC-SHA-256은 메시지와 공유 비밀키로 인증 태그를 만든다. 비절단 태그는 32바이트다. 검증자는 수신 메시지로 태그를 다시 계산하고 `hmac.compare_digest`로 비교한다.

```python
tag = hmac.digest(key, message, 'sha256')
ok = hmac.compare_digest(tag, hmac.digest(key, received, 'sha256'))
```

`SHA256(key || message)`를 직접 만드는 대신 HMAC을 쓴다. SHA-256의 단순 접두 키 해시는 길이 확장 공격에 취약한 구성이고, 표준 HMAC은 같은 방식의 길이 확장이 성립하지 않도록 구성된다.

| 배포 방식 | 유출 영향 | 남는 한계 |
|---|---|---|
| 전 장치 공통 공유키 | 그 키를 신뢰하는 모든 장치 | 검증자도 태그 생성 가능 |
| 장치별 공유키 | 해당 키를 사용하는 장치 | 검증자도 태그 생성 가능 |
| 공개키 서명 | 공개 검증키 노출만으로 서명 불가 | 개인키 통제·검증키 승인 필요 |

유출된 공유키로 임의 메시지에 새 태그를 붙이면 검증이 통과한다. 이는 HMAC 알고리즘을 깨뜨린 결과가 아니라 키 보호 가정이 깨진 결과다. 배포 주체의 생성 권한과 단말의 검증 권한을 분리하려면 비대칭 서명을 검토한다.

## 4. 전자서명과 공개키 승인 (PART 05~06)

Ed25519에서는 개인키로 서명하고 공개키로 검증한다. 공개키는 32바이트, 서명은 64바이트다. 서명 주체가 개인키를 보관하고 배포 서버는 이미 서명된 결과를 전달할 수 있다.

| 입력 | 검증키 | 결과 |
|---|---|---|
| 원본 + 발행자 서명 | 사전 승인한 발행자 키 | 통과 |
| 변경 파일 + 원본 서명 | 발행자 키 | 서명 실패 |
| 공격자 서명 | 발행자 키 | 서명 실패 |
| 공격자 파일·서명·공개키를 함께 교체 | 동봉 키를 무조건 사용 | 수학적 서명 검사 통과 |

마지막 경우 공개키의 출처를 확인하지 않았다. 검증 성공은 주어진 공개키와 바이트열·서명의 관계를 말할 뿐, 공개키가 승인된 제조사 것이라는 의미는 아니다.

전자서명은 무결성과 출처 확인에 쓰이며 내용을 암호화하지 않는다. 부인방지 역시 키 귀속·통제·운영 증거가 전제되는 성질이다.

## 5. PKI와 TLS 서버 인증 (PART 06)

인증서는 주체, 공개키, 유효기간, 제약·용도 등을 발급자 서명으로 묶는다. 사전 신뢰한 Root에서 중간 CA와 종단 인증서로 검증 경로를 이어 간다. Root의 자기서명만으로 신뢰가 새로 생기지는 않는다.

| 검사 | 확인 내용 |
|---|---|
| 경로·서명 | 단말이 이미 신뢰한 기점에 연결되는가 |
| 기간 | 신뢰 가능한 기준 시각이 유효기간 안인가 |
| 제약 | Basic Constraints·Key Usage·경로 길이 등 |
| 용도 | 펌웨어 서명용 codeSigning / 서버용 serverAuth 정책 |
| 폐기 | 적용한 CRL·OCSP 등 폐기 확인 정책 |

TLS 서버 인증에서는 인증서 경로와 접속 이름(SAN)을 확인하고, 핸드셰이크에서 개인키 소유를 확인한다. TLS 1.3의 `CertificateVerify`는 인증서 키의 소유 증명에, `Finished`는 핸드셰이크 무결성과 키 확인에 사용된다.

| 축 | 펌웨어 서명 | TLS 서버 인증 |
|---|---|---|
| 질문 | 이 배포물을 누가 승인했는가 | 지금 연결한 서버는 누구인가 |
| 대상 | 저장·중계 가능한 배포물 | 현재 통신 세션 |
| 신뢰 기준 | 서명자 신뢰와 사용 권한 | 서버 인증용 신뢰 저장소·예상 이름 |
| 세션 종료 후 | 배포물 검증 가능 | 해당 세션의 보호 종료 |

두 신뢰 기점은 같을 필요가 없다. TLS 통과만으로 패키지 설치 권한이 생기지 않고, 서명 통과만으로 접속 상대가 확인되지 않는다. TCP 접속 주소와 검증할 서버 이름도 구분한다.

## 6. 신뢰 기점 보호와 키 수명 (PART 07)

공개 검증키는 비밀일 필요가 없지만 무단 변경은 막아야 한다. 개인키는 비밀성과 사용 권한을 함께 보호한다.

| 수단 | 맡는 역할 | 구분할 점 |
|---|---|---|
| ROM | 초기 검증 코드의 불변 기반 | 키 저장과 동일 기능이 아님 |
| OTP·eFuse | 초기 공개키 해시 등 되돌릴 수 없는 기준 | 기록 권한과 시점 설계 필요 |
| 접근 제어·보호 저장 | 운영 신뢰 집합의 승인된 변경 | 운영 정보는 갱신 가능해야 함 |
| HSM·Secure Element | 키 반출·사용 제한과 보안 연산 | 칩 내부/별도 칩 등 구현에 따름 |
| TrustZone·TEE | 일반 실행 영역과 보안 서비스 분리 | TrustZone은 하드웨어, TEE는 실행 환경 |

인증서 갱신, 서명키 교체, 운영 Root 교체, 침해 복구를 구분한다. 인증서 갱신에 같은 키를 유지할 수 있지만 항상 그렇다는 뜻은 아니다. 동일 Root 아래 새 서명 인증서가 유효해도 별도 승인 목록이 있다면 그 목록도 갱신해야 한다.

공개키 고정은 경로·이름 검증에 추가하는 제한 정책으로 설명된다. 종단 키를 고정하면 정상 키 교체에도 고정값 갱신 경로가 필요하다. 인증서 전체 고정과 공개키 해시 고정을 혼용하지 않는다.

## 7. 신뢰 상태 전환과 침해 복구 (PART 08)

정상 전환의 교육용 예는 `epoch 1: [A] → epoch 2: [A,B] → epoch 3: [B]`다. 현재 승인 권한으로 새 공개키 집합과 새 세대를 승인한다. 키 이름 문자열만이 아니라 실제 공개키 또는 정의된 인코딩의 해시를 결합해야 한다.

| 상태 | 필요한 통제 |
|---|---|
| 새 Root의 자기서명 | 별도 승인 없이는 등록하지 않음 |
| 정당한 최신 갱신 | 현재 승인권한·이전 세대·새 세대 검증 |
| 과거 정상 스냅샷 재주입 | 보호된 현재 세대보다 작으면 거부 |
| 운영 개인키 유출 | 그 키의 서명만으로 복구 승인하지 않음 |
| 복구 완료 이후 | 폐기된 키 재등록과 과거 세대 복원을 차단 |

운영 키가 탈취되면 발행자의 전이와 공격자의 전이 모두 같은 키로 서명 검증을 통과할 수 있다. 이때 사전 마련한 독립 복구 권한과 승인 절차가 필요하다. 단순 대역 외 전달만으로 안전한 승인이 되는 것은 아니다.

## 8. Secure Boot와 실행 중 보호 (PART 09)

다운로드 검증 후 저장 이미지가 바뀔 수 있으므로 실행 직전에도 승인 여부를 검사한다. 부팅 단계마다 다음 단계가 실행할 이미지를 검증하고 통과한 경우에만 제어를 넘긴다. 최초 검증 코드와 기준은 더 강하게 보호된 ROM·OTP 등의 기반에서 시작한다.

Secure Boot가 통과해도 런타임 취약점이 없어지는 것은 아니다. 신뢰 집합, 보안 하한, 폐기 상태, 검증 코드, 단말 비밀키를 일반 응용의 쓰기 권한에서 분리한다. TEE 서비스 호출도 호출자 권한과 인자 검증이 필요하다.

MCU에서는 OS 없이 부트로더와 응용으로 구성할 수도 있다. 보안 코어/HSM이 호스트 이미지를 검증하고 실행을 허용하는 방식도 있다. 강의의 여러 부팅 순서는 플랫폼별 예시다.

## 9. 다운로드 중단과 재개 (PART 10~11)

이상적인 전송 시간은 `파일 비트 수 / 전송률`이다. 예를 들어 8 MiB는 67108864비트이며 0.5 Mbit/s에서 약 134.2초다. 프로토콜·암호화·재전송 오버헤드는 빠진 하한값이다.

512 KiB 이미지를 64 KiB씩 나누면 8청크다. 청크 `i`의 시작은 `i × chunk_size`, 끝은 `min(size, (i+1) × chunk_size)-1`이다. 마지막 청크는 짧을 수 있다.

| 저장 정보 | 역할 |
|---|---|
| 서명된 매니페스트 | 크기·청크 크기·청크 해시·전체 해시의 인증된 기준 |
| 매니페스트 식별자 | 이어 받는 이미지의 동일성 판단 |
| 로컬 수신 기록 | 어느 구간을 받았는지 기록 |
| 저장된 청크 | 현재 바이트를 재검증할 대상 |

완료 플래그는 현재 파일이 온전하다는 증거가 아니다. 0~4를 받은 뒤 청크 2가 손상되면 재요청 대상은 `2,5,6,7`이다. 정상으로 재검증된 0·1·3·4는 재사용한다.

HTTP Range 응답에서는 `206`, `Content-Range`, 실제 길이를 확인한다. Range를 무시한 `200` 응답을 기존 부분 파일 뒤에 붙이지 않는다. 청크 검증 후 재조립 결과를 전체 해시로 다시 확인한다.

## 10. 매니페스트와 서명 바이트열 (PART 12)

| 필드 | 용도 |
|---|---|
| `target`, `hardware_revision` | 대상과 하드웨어 적합성 |
| `version` | 사람이 읽는 릴리스 식별자 |
| `security_version` | 보안 정책 비교값 |
| `size`, `payload_hash` | 실제 이미지 길이·전체 해시 |
| `chunk_size`, `chunk_hashes` | 부분 재개와 청크 검증 |
| `requires` | 다중 ECU 선행 조건의 예 |

이미지는 `payload_hash`를 통해 매니페스트 서명과 결합된다. 설치 조건과 이미지 해시를 함께 서명해야 서로 다른 정품 요소를 잘못 섞는 것을 방지할 수 있다.

같은 JSON 값이어도 공백·키 순서가 달라지면 서명 입력 바이트가 달라진다. 생성자는 약속한 직렬화로 한 번 생성·서명하고, 수신자는 **수신 원본 바이트를 검증한 뒤 파싱**한다. `sort_keys=True`, `separators=(',', ':')`는 실습 규칙이며 완전한 JSON 정규화 표준은 아니다.

중복 키, 필드 타입, 크기 상한, 청크 수, 해시 형식도 검사한다. 서명이 유효한 비정상 입력이 시스템 자원을 소진하거나 파서의 모호성을 유발하지 않도록 한다.

## 11. 단계별 검증과 설치 조건 (PART 12~13)

```text
signature → signer → schema/policy → chunk → image → 기록 후 확인 → boot → health → commit
```

| 판정 | 대표 거부 사유 | 조작 조건 |
|---|---|---|
| 서명 | `SIGNATURE_INVALID` | 원본 서명을 유지한 채 매니페스트 바이트 변경 |
| 서명자 | `SIGNER_NOT_AUTHORIZED` | 비승인 키가 자기 키로 유효하게 서명 |
| 대상 | `TARGET_MISMATCH` | 승인 발행자가 다른 대상용으로 정상 서명 |
| HW | `HARDWARE_MISMATCH` | 대상은 같으나 하드웨어 리비전 다름 |
| 보안 세대 | `SECURITY_VERSION_TOO_LOW` | 정상 서명된 구버전 재전송 |
| 청크 | `CHUNK_HASH_REJECTED` | 수신·저장된 특정 청크 손상 |
| 이미지 | `PAYLOAD_HASH_REJECTED` | 청크 검증 후 재조립 결과 손상 |

첫 실패에서 처리를 중단한다. 공격자가 target만 바꾸고 서명을 유지하면 대상 단계가 아니라 서명 단계에서 실패한다. 전체 해시 단계를 시험하려면 손상을 청크 검증 이후 주입한다.

설치 직전에는 전원·저장 공간·차량 사용 상태 등 현재 전제조건도 다시 확인한다. 강의의 metadata-first는 채택한 설계이며 다른 수신 순서가 모두 오류라는 뜻은 아니다.

## 12. 보안 버전과 롤백 방지 (PART 14)

정품 구버전은 서명과 해시를 모두 통과한다. 설치 허용은 `incoming.security_version >= security_floor`로 따로 판단한다. `version='2.4.0'`과 `security_version=6`은 다른 축이다.

보안 하한이 일반 파일에 있고 공격자가 이를 6에서 5로 낮출 수 있으면 구버전 5가 다시 통과한다. 하한은 이미지 갱신 권한과 분리하고, 승인된 확정 시점에만 증가시킨다. RPMB는 인증된 접근과 저장 데이터의 재전송 방지를 제공하지만 값의 감소 금지는 신뢰된 코드 정책이 별도로 강제해야 한다.

## 13. 설치 중단과 A/B 구조 (PART 15~17)

| 방식 | 중단 시 남는 이미지 | 과제 |
|---|---|---|
| 단일 영역 덮어쓰기 | 새 앞부분 + 기존 뒷부분 | 별도 복구 없이 실행 가능한 정상본이 사라질 수 있음 |
| A/B 슬롯 | 확정 A 보존 + 부분 기록 후보 B | 후보 검증·선택 정보·확정 절차 필요 |
| 복구 이미지 | 갱신에서 제외된 복구 환경 | 복구 이미지의 승인과 접근 경로 필요 |
| 부트로더 복구 | 재기록 경로 | 부트로더·전송·정책 보호 필요 |

교육용 중단은 524288바이트 슬롯의 앞 262144바이트만 덮어쓴다. 슬롯 길이는 그대로이므로 길이 검사만으로 부분 기록을 발견할 수 없다. 전체 이미지 해시와 승인 상태를 확인한다.

Staging은 수신 임시 영역이다. 실행 슬롯과 분리되어도 이후 활성 슬롯을 덮어쓰는 설치 과정의 보존 문제는 별도로 남는다. A/B는 비활성 실행 슬롯을 기록하고 후보를 전환한다.

## 14. 부팅 메타데이터 (PART 16)

| 상태 | 항목 | 보호 목적 |
|---|---|---|
| 확정 기록 | `confirmed_slot`, `security_floor` | 승인된 실행 상태와 보안 정책의 일관성 |
| 후보 정보 | `candidate_slot`, `attempts_left` | 시험 부팅과 소진 후 배제 |
| 사본 관리 | `seq`, `magic`, `crc32` | 구조·세대 선택과 우발 손상 검사 |

두 사본을 번갈아 갱신하며 현재 유효 사본을 먼저 지우지 않는다. 재시작 시 구조와 체크값이 유효한 사본 가운데 일관된 최신 세대를 고른다. 둘 다 무효하면 지정 복구 경로로 간다.

CRC는 공격자의 변경을 인증하지 않는다. 공격자는 CRC도 다시 계산할 수 있다. 두 사본이 있다는 사실만으로 원자성도 생기지 않는다. 기록 단위, 갱신 순서, 완료 판정, 재시작 선택 규칙과 쓰기 권한 보호가 함께 필요하다.

## 15. 시험 부팅과 Health Check (PART 18)

```text
IDLE → DOWNLOADED → VERIFIED → INSTALLED → BOOT_PENDING → TESTING
                                                            ├─ 동작 성공 → COMMITTED
                                                            └─ 시도 소진 → RECOVERY
```

Secure Boot는 승인 이미지를 실행하는지 확인하고, Health Check는 필수 서비스·설정·응답 기한 등의 동작 조건을 확인한다. 승인된 이미지에도 기동 실패가 있을 수 있다.

후보 등록 때 3회를 한 번 설정한다. 매 시험 부팅 **직전** 횟수를 줄이고 저장한 뒤 제어를 넘긴다. 실패 보고 후에만 줄이면 보고 전 리셋으로 무한 재시도가 가능하다. 영구 서명 오류는 즉시 후보에서 제외할 수 있다.

`confirmed_slot=A`, `candidate_slot=B`, `booted_slot=B`가 동시에 성립할 수 있다. 현재 실행과 확정 상태를 같은 변수로 표현하지 않는다.

## 16. 복구 정책과 보안 상태 일관성 (PART 19)

기존 A의 보안 버전이 5, 후보 B가 6일 때 시험 중 하한은 5를 유지한다. B가 실패하면 정책상 허용되는 A로 복구한다. 동작 확인 전 하한을 6으로 올리면 A가 `5 < 6`으로 거부되어 `RECOVERY_FORBIDDEN`이 된다.

확정 시에는 `confirmed_slot=B`와 `security_floor=6`을 하나의 논리적 확정 상태로 관리한다. 다른 저장 장치에 두면 물리적으로 동시에 쓰는 것이 아니므로 중단 후 복원 절차가 필요하다.

신뢰 epoch·폐기 목록을 슬롯 이미지와 함께 되돌리지 않는다. 이미지 복구가 폐기 키를 되살리지 않도록 보안 상태의 수명을 분리한다. `attempts_left`는 감소하지만 epoch와 보안 하한은 후퇴하지 않는다.

업데이트 실패와 복구 성공은 독립 결과다. 승인된 복구 대상이 없으면 하한을 임의로 낮추지 말고 별도 승인 복구 경로나 복구 모드로 전환한다.

## 17. 다중 ECU와 신뢰 경계 (PART 20)

| 역할 | 책임 |
|---|---|
| 배포 측 | 패키지 승인·캠페인·대상별 배포 정책 |
| 차량 조정자 | 패키지 전달·의존성·활성화 순서·진행 기록 |
| 대상 ECU | 자기 대상·이미지·설치 조건과 실행 승인 |

역할과 장치는 일대일일 필요가 없다. 직접 검증은 대상 ECU가 서명·정책을 확인하고, 대행 검증은 게이트웨이가 일부 검증을 대신한다. 대행 방식은 게이트웨이와 ECU 사이 전달 경로 및 승인 정보에 추가 신뢰가 필요하다. 부팅 검증이 모든 차이를 자동으로 보완하지 않는다.

CAN·LIN·Ethernet 같은 전송 기술과 A/B·부트로더 설치 구조는 독립적인 설계 축이다.

## 18. 의존성·전환 경로·캠페인 (PART 21)

강의의 A2는 B4 이상을 요구한다. 아래 축약은 ECU 릴리스의 교육용 표기이며 단일 단말의 보안 버전 5·6과 다른 값이다.

| 차량 구성 | 의존 조건 | 승인 목록 | 판정 |
|---|---|---|---|
| A1/B3/C1 | 해당 없음 | 등재 | 허용 |
| A1/B4/C1 | 해당 없음 | 등재 | 허용 |
| A2/B3/C1 | 불만족 | 미등재 | `DEPENDENCY_REJECTED` |
| A2/B4/C1 | 만족 | 등재 | 허용 |
| A2/B5/C1 | 만족 | 미등재 | `CONFIG_NOT_APPROVED` |
| A2/B4/C2 | 만족 | 등재 | 목표 구성 |

허용 경로는 `A1/B3/C1 → A1/B4/C1 → A2/B4/C1 → A2/B4/C2`다. A를 먼저 활성화하면 A2/B3/C1에서 의존 조건을 위반한다. 최종 구성뿐 아니라 중간 구성과 복귀 경로도 검사한다.

C2 설치가 실패해 A2/B4/C1에 남으면 구성은 허용되지만 목표 A2/B4/C2에 도달하지 못해 캠페인은 `INCOMPLETE`, 확정은 `BLOCKED`다. 복구 계획 출력과 실제 ECU 복구 완료는 다른 일이다.

## 19. 산업 표준의 역할 (PART 22)

| 자료 | 역할 | 이 노트의 대응 |
|---|---|---|
| Uptane | 업데이트 메타데이터 신뢰·역할 분리 | Root·Targets와 신뢰 집합·매니페스트 개념 |
| AUTOSAR | 플랫폼의 업데이트 인터페이스·기능 규격 | 조정·대상·설치 역할 분리 |
| ISO 24089 | 소프트웨어 업데이트 공학 | 승인·호환성·기록·실패 관리 관점 |
| UN R156 | 업데이트·관리 체계의 형식승인 요구 | 기술 요소와 관리 체계의 구분 |

Uptane의 Image Repository와 Director Repository를 구분하며 완전 검증은 두 저장소의 메타데이터를 대조한다. Root·Targets·Snapshot·Timestamp는 역할별 서명 대상이 다르다. 강의의 매니페스트 실습은 Snapshot·Timestamp 전체 검증을 구현하지 않는다.

이 절은 **첨부 강의의 개념 소개 범위**다. 최신 판본·적용 국가·의무화 시점·조항 해석을 다루지 않고, 실습 통과가 표준 준수나 형식승인 증거라는 의미도 아니다.

## 20. 학습 점검

| 질문 | 답변의 핵심 |
|---|---|
| SHA-256만으로 발행자를 알 수 있는가 | 인증된 기준값이 필요 |
| MAC 검증자에게 생성 권한도 있는가 | 같은 공유키로 생성 가능 |
| 서명 검증 성공이면 설치 가능한가 | 승인 키·대상·HW·보안 정책·이미지·현재 조건 별도 |
| TLS가 패키지 서명을 대체하는가 | 세션과 배포물의 보호 대상이 다름 |
| Secure Boot가 정상 서비스까지 보장하는가 | Health Check 별도 |
| CRC가 공격자의 메타데이터 변경을 막는가 | 우발 손상 검사이며 인증 아님 |
| 정상 복구라면 보안 하한을 낮춰도 되는가 | 현재 정책을 만족하는 승인 경로 필요 |
| 모든 ECU가 정품이면 조합도 허용되는가 | 의존성·승인 구성·전환 경로 별도 |
| 허용 구성에 남으면 캠페인도 완료인가 | 필수 목표·설치·동작 결과 충족 별도 |

출처와 구현 범위는 [문서 안내](./README.md)에 기록했다.
