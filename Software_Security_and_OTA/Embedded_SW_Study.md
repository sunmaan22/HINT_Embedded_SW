## 1. 신뢰 입력과 비신뢰 입력

| 구분 | 예 | 사용 규칙 |
|---|---|---|
| 전달 받은 데이터 | 이미지·매니페스트·서명·동봉 인증서 | 승인 판정 전까지 비신뢰 |
| 단말의 사전 기준 | 서명자 목록·TLS Root·대상·HW | 배포물로 임의 교체하지 않음 |
| 보호된 보안 상태 | 하한·epoch·폐기 정보 | 승인된 경로로만 변경 |
| 로컬 진행 기록 | 청크 수신 플래그·부팅 후보 | 현재 데이터 재검증 필요 |
| 동작 관측 | 서비스 응답·시험 부팅 결과 | 암호 검증으로 대신하지 않음 |

네트워크 데이터를 바로 플래시 기록 함수에 넘기지 않는다. 크기 제한을 먼저 적용하고 원본 바이트 서명·서명자 권한·스키마·정책을 확인한다. 설치 직전 현재 정책과 자원 조건도 다시 확인한다.

## 2. 바이트열의 수명

전자서명은 JSON 객체가 아니라 바이트열에 걸린다. 서명 전에 직렬화하고 검증 전에 원본 바이트를 재직렬화하지 않는다. 코드에서는 매니페스트 읽기 크기를 제한하고 중복 키를 거부한다.

| 경계 | 검토할 것 |
|---|---|
| HTTP → 매니페스트 | 최대 길이·수신 완료·원본 바이트 |
| 서명 → 파서 | 검증된 바이트와 파싱한 바이트가 같은가 |
| 파서 → 정책 | bool을 정수로 허용하지 않는 타입 검사 |
| 청크 → 재조립 | 순서·마지막 길이·전체 길이 |
| 검증 → Writer | 검사 뒤 바이트가 바뀌지 않는가 |
| Writer → 부팅 | 기록 후 재읽기·다음 부팅 검증 |

강의 예제의 JSON 직렬화 규칙을 그대로 모든 서명 프로토콜에 적용하지 않는다. 실제 시스템에서는 포맷·버전·알고리즘·인코딩을 합의해야 한다.

## 3. 다운로드 재개의 조건

매니페스트 ID는 승인된 매니페스트 원본 바이트의 SHA-256으로 정의한다. 재개 상태가 다른 ID를 가리키면 청크를 섞지 않는다. 완료 표시가 있어도 각 저장 청크의 길이·해시를 다시 계산한다.

```text
초기 수신: 0 1 2 3 4
손상 주입:     2
재사용:   0 1   3 4
재요청:       2     5 6 7
```

로컬 `download_state.json`에 복사한 해시를 새로운 신뢰 기준으로 사용하지 않는다. 신뢰 기준은 검증한 매니페스트다. 네트워크 예제는 `206`과 정확한 Content-Range, 응답 길이를 모두 검사한다.

## 4. A/B 설치와 기록 후 검사

확정 슬롯은 갱신 쓰기의 대상에서 제외한다. 비활성 슬롯에 기록한 뒤 다시 읽어서 승인 이미지 해시를 확인하고, 통과한 뒤에만 후보를 등록한다.

| 중단 지점 | 남는 상태 | 재시작 판정 |
|---|---|---|
| 수신 중 | Staging의 일부 청크 | 검사 후 필요한 청크만 재요청 |
| 후보 기록 중 | 확정 A + 부분 B | B 제외·A 검사 후 실행 |
| 후보 정보 기록 중 | 이전 유효 사본 + 미완성 사본 | 유효한 사본 선택 |
| 시험 부팅 중 | 차감된 횟수 + 미확정 후보 | 남은 횟수로 재시도 또는 복구 |
| 확정 기록 중 | 이전/새 논리적 확정 기록 | 일관된 유효 기록 선택 |

파일 기반 예제의 `flush/fsync`와 `os.replace`는 운영체제 파일 동작이다. 플래시 erase/program 단위나 실제 전원 손실 시의 영속성을 입증하지 않는다.

## 5. 부팅 메타데이터와 보안 상태

코드는 후보 정보를 `meta0.json`과 `meta1.json`에 번갈아 저장하며 CRC를 검사한다. 확정 슬롯과 하한은 별도 `confirmed.json`에 묶고, 신뢰 세대는 실행 슬롯과 분리한다.

| 필드 | 갱신 방향 | 의미 |
|---|---|---|
| `seq` | 증가 | 후보 사본의 최신 세대 |
| `attempts_left` | 감소 | 제어 이양 전에 저장 |
| `candidate_slot` | 등록·삭제 | 미확정 시험 대상 |
| `confirmed_slot` | 확정 때 변경 | 마지막으로 동작 확인한 슬롯 |
| `security_floor` | 유지·증가 | 설치와 복구의 허용 하한 |
| `epoch` | 증가 | 현재 신뢰 상태의 세대 |

확정 기록의 JSON 파일은 보호 저장소의 **모의 모델**이다. 파일 접근 권한이 있는 공격자는 변경할 수 있다. CRC·해시·두 사본이 보안 권한 보호를 대신하지 않는다.

## 6. Boot · Health · Commit 분리

1. 슬롯을 읽고 매니페스트 서명·권한·정책·전체 해시를 다시 확인한다.
2. 시험 부팅 횟수를 감소·저장한다.
3. 후보로 제어를 넘긴다고 모의 기록한다.
4. Health Check가 성공하면 후보 슬롯과 하한을 함께 확정한다.
5. 실패하면 확정 상태를 유지하고 횟수 소진 시 승인된 복구 대상을 검사한다.

복구 슬롯이 하한보다 낮으면 실행하지 않는다. `booted_slot` 출력은 교육용 선택 결과이며 실제 MCU의 PC 전환이나 차량 기능 수행 결과가 아니다. Health Check는 실습 인자로 주입하는 관측값이다.

## 7. 진단 결과를 읽는 기준

| 결과 | 뜻 | 뜻하지 않는 것 |
|---|---|---|
| 서명 PASS | 주어진 키로 바이트 서명이 유효 | 그 키의 사용 권한 승인 |
| 청크 PASS | 인증된 기준과 해당 구간 일치 | 조립 순서·전체 이미지까지 정상 |
| 설치 PASS | 후보 기록·재검사 완료 | 서비스 기동 성공 |
| 부팅 검증 PASS | 저장 이미지가 승인 조건 충족 | 런타임 취약점 없음 |
| Health PASS | 정한 동작 관측값 충족 | 차량 기능안전 검증 완료 |
| old_preserved=True | 기존 파일 바이트 보존 | 현재 정책상 복구 가능 |
| configuration=ALLOWED | 현재 조합 허용 | 캠페인 목표 도달 |

첫 실패 단계와 거부 코드를 기록하고, 업데이트 결과와 복구 결과를 별도 항목으로 남긴다.

## 8. 다중 ECU 조정

패키지별 암호 검증 이후 활성화 경로 전체를 검사한다. 예제는 B→A→C 순서이고 각 단계의 실제 구성을 확인한다. C 실패는 C1 유지로 모델링하며 전체 캠페인 확정을 막는다.

실제 ECU 기록·진단 전송·정전·통신 재시도·전체 차량 복구는 별도 구현 과제다. 구성 계산 프로그램이 실행되었다는 사실만으로 세 ECU 설치가 수행된 것은 아니다.

| 범주 | 실행하는 확인 |

| 인증 | 원본·변경 파일·다른 키·동봉 키 교체 |
| 입력 | 공백 변경·중복 키·타입 오류·크기 상한·짧은 마지막 청크 |
| 정책 | 대상·HW·구버전 거부 |
| 재개 | 손상 2 + 미수신 5·6·7 재요청·최종 해시 |
| 설치 | 단일 영역/A-B 부분 기록 비교·별도 프로세스 상태 재읽기 |
| 메타데이터 | 한 사본 손상·두 사본 손상·구조 오류 거부 |
| 시험 부팅 | 횟수 소진·확정 시 하한 상승·조기 상승 복구 거부 |
| 신뢰 | 세대 후퇴·폐기 키 재등록·침해 시 독립 복구권한 |
| 차량 구성 | 의존성·미승인 목표·잘못된 순서·C 실패 |
| PKI/TLS | 정상 경로·만료·용도·비신뢰 Root·서버 이름 불일치·Range |
