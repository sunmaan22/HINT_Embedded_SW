# MCU Programming

ATmega128A 기반 실습을 통해 레지스터 제어, 인터럽트, 통신, 주기 실행과 센서 처리를 정리한 기술 노트이다. 각 기능은 **무엇을 하는지**, **어떤 레지스터로 제어하는지**, **드라이버와 응용 프로그램이 어떻게 연결되는지**를 중심으로 설명한다.

## 2. MCU의 실행 구조와 메모리

일반적인 PC 응용 프로그램은 운영체제가 제공하는 프로세스와 입출력 서비스를 사용한다. 이 실습의 MCU 프로그램은 리셋 후 시작 코드가 메모리를 준비하고 `main()`에 진입하며, 초기화 이후 반복 루프에서 입력과 제어 작업을 수행한다.

### 메모리의 역할

| 영역 | ATmega128A 용량 | 용도와 고려 사항 |
|---|---|---|
| Flash | 128 KB | 프로그램과 초기값을 보관한다. AVR의 프로그램 메모리 접근 방식을 구분해야 한다. |
| SRAM | 4 KB | 실행 중 변수와 스택을 저장한다. 정적 데이터뿐 아니라 함수 호출과 ISR의 스택 사용량도 고려한다. |
| EEPROM | 4 KB | 전원 차단 후에도 유지할 설정값을 저장하는 데 사용한다. |

`.data`의 초기값은 시작 시 Flash에서 SRAM으로 복사되고, `.bss`는 0으로 초기화된다. 따라서 초기값이 있는 전역 데이터는 Flash와 SRAM 사용량에 모두 영향을 준다. AVR-GCC에서 큰 상수 테이블이나 문자열을 Flash에 유지하려면 `PROGMEM`과 그에 맞는 접근 방법을 검토한다.

### 데이터 주소 공간

| 데이터 주소 | 영역 | 의미 |
|---|---|---|
| `0x0000 ~ 0x001F` | 범용 레지스터 | CPU의 R0 ~ R31 |
| `0x0020 ~ 0x005F` | I/O 레지스터 | GPIO 등 주변장치 제어·상태 레지스터 |
| `0x0060 ~ 0x00FF` | 확장 I/O 레지스터 | 추가 주변장치 레지스터 |
| `0x0100 ~ 0x10FF` | 내부 SRAM | 변수와 스택 |

I/O 명령에서 사용하는 주소와 C 포인터가 사용하는 데이터 주소는 구분해야 한다. 일반 I/O 영역은 **데이터 주소 = I/O 주소 + 0x20** 관계를 가지며, 확장 I/O는 데이터 주소를 기준으로 확인한다.

## 3. 레지스터 직접 접근과 volatile

주변장치는 제어 레지스터로 동작을 설정하고, 상태 레지스터로 진행 상황을 확인하며, 데이터 레지스터로 값을 전달한다. **Memory-mapped I/O**는 이런 레지스터를 데이터 주소 공간에 배치하여 메모리 접근으로 제어하는 방식이다.

| 레지스터 | I/O 주소 | 데이터 주소 | 역할 |
|---|---|---|---|
| `PINB` | `0x16` | `0x36` | PORTB 핀 입력 상태 |
| `DDRB` | `0x17` | `0x37` | PORTB 입출력 방향 |
| `PORTB` | `0x18` | `0x38` | PORTB 출력값·입력 풀업 설정 |

`<avr/io.h>`의 레지스터 이름은 장치별 주소에 접근하기 위한 매크로이다. [myreg.h](./DAY1/AM/myreg.h)는 직접 주소를 정의하는 방식을, [myboard.h](./DAY1/AM/myboard.h)는 그 주소와 보드의 LED 배선을 연결하는 방식을 보여준다.

**volatile**은 하드웨어나 ISR에 의해 값이 바뀔 수 있는 객체의 접근을 컴파일러가 임의로 생략하지 않도록 하는 데 사용한다. 그러나 여러 명령으로 이루어진 연산 전체를 원자적으로 만들지는 않는다. 공유 데이터 보호는 별도의 임계구역 설계가 필요하다.

## 4. 비트 조작과 GPIO

레지스터 하나에는 서로 다른 기능의 비트가 함께 들어간다. 전체 값을 덮어쓰면 다른 핀이나 설정까지 바뀔 수 있으므로, 변경할 비트만 마스크로 선택한다.

| 목적 | C 표현 | 의미 |
|---|---|---|
| 비트 설정 | `reg |= mask` | 마스크에 해당하는 비트를 1로 설정 |
| 비트 해제 | `reg &= ~mask` | 마스크에 해당하는 비트를 0으로 설정 |
| 비트 반전 | `reg ^= mask` | 선택한 비트의 값을 반전 |
| 상태 검사 | `(reg & mask) != 0` | 선택한 비트 중 1이 있는지 확인 |
| 필드 교체 | `(reg & ~mask) \| ((value << shift) & mask)` | 다른 필드를 보존하고 지정 필드만 변경 |

### GPIO 레지스터와 보드 극성

`DDRx`는 방향, `PORTx`는 출력값 또는 입력 풀업 설정, `PINx`는 핀 상태 확인에 사용한다. 입력 모드에서 풀업이 실제로 동작하는지는 칩의 관련 설정도 함께 확인해야 한다.

이 보드의 PB0 ~ PB7 LED는 **Active-Low**이므로 핀 출력 0이 점등을 의미한다. 드라이버는 이 극성을 내부에서 처리하여 응용 프로그램이 논리적인 켜짐·꺼짐만 다루도록 만든다.

**Read-Modify-Write(RMW)**는 읽기, 수정, 쓰기가 결합된 연산이다. ISR과 같은 레지스터를 수정하면 갱신이 유실될 수 있으므로 생성 명령과 공유 범위를 확인한다. W1C처럼 1을 써서 지우는 상태 비트에는 일반 변수용 RMW 규칙을 그대로 적용하지 않는다.

구조체·공용체는 레지스터 묶음을 표현하는 데 사용할 수 있지만, 주소 간격과 패딩을 검토해야 한다. C 비트필드의 배치와 접근 방식은 구현에 의존하므로 하드웨어 제어에서 이식성을 당연하게 가정하지 않는다.

## 5. 드라이버 계층과 보드 구성

응용 프로그램은 모드와 동작 순서를 결정하고, 드라이버는 레지스터 접근과 장치별 처리 규칙을 담당한다. 핀 배치는 보드 정의에 모아 배선 변경의 영향을 줄인다.

| 구성 | 역할 | 현재 코드 예 |
|---|---|---|
| 응용 프로그램 | 입력에 따라 패턴·모드·명령 처리 결정 | `homework*.c` |
| 드라이버 인터페이스 | 외부에 제공하는 함수와 이벤트 정의 | `led.h`, `btn.h`, `uart.h` |
| 드라이버 구현 | GPIO 조작, 인터럽트 처리, 송수신 구현 | `led.c`, `btn.c`, `fnd.c`, `uart.c` |
| 보드 정의 | 포트, 핀, 극성과 클럭 설정 관리 | `board.h`, `myboard.h` |
| 레지스터 정의 | 장치 주소와 비트 이름 제공 | `<avr/io.h>`, `myreg.h` |

### 주요 핀 연결

| 장치 | 보드 연결 | 소프트웨어에서의 의미 |
|---|---|---|
| LED D1 ~ D8 | PB0 ~ PB7 | Active-Low 출력 |
| 버튼 SW2 ~ SW5 | PE4 ~ PE7, INT4 ~ INT7 | Active-Low 입력과 외부 인터럽트 |
| FND | 세그먼트 PORTC, 자리 선택 PD4 ~ PD7 | 세그먼트 출력과 자리 선택 분리 |
| USART1 | RXD1 PD2, TXD1 PD3 | 보드 USB 직렬 인터페이스 |
| PWM LED D9 | PE3, OC3A | Timer3 출력, Active-Low |
| 가변저항 VR3 | PF0, ADC0 | 수동 밝기 입력 |
| 조도센서 CDS | PF1, ADC1 | 밝기 측정 입력 |
| 문자 LCD | 데이터 PORTA, 제어 PG0 ~ PG2 | 상태와 센서값 표시 |

핀 표는 저장소의 [board.h](./DAY2/PM/board.h)를 기준으로 한다. 다른 보드에서는 같은 ATmega128A를 사용하더라도 연결과 극성이 달라질 수 있다.

## 6. 인터럽트와 공유 데이터

폴링은 프로그램이 상태를 반복 확인하는 방식이고, 인터럽트는 주변장치의 요청에 따라 지정된 처리 루틴으로 실행 흐름이 이동하는 방식이다. 인터럽트를 사용하면 긴 반복 루프 사이에 발생한 입력을 포착할 수 있지만, 실제 처리 지연과 데이터 보존은 소프트웨어 구조에 달려 있다.

| 요소 | 역할 |
|---|---|
| 인터럽트 벡터 | 요청 종류와 처리 루틴 연결 |
| `EICRB` | INT4 ~ INT7의 감지 조건 설정 |
| `EIMSK` | 외부 인터럽트별 허용 |
| `EIFR` | 외부 인터럽트 요청 플래그 |
| `SREG`의 I 비트 | 전역 인터럽트 허용 상태 |
| `ISR(...)` | AVR 도구 체인에서 ISR 함수를 정의하는 매크로 |

ISR에서는 필요한 데이터 읽기와 이벤트 기록을 짧게 수행하고, 문자열 출력·명령 해석·상태 판단은 메인 루프로 넘긴다. 버튼 입력에는 채터링이 있으므로 인터럽트만 적용한다고 한 번의 누름이 한 이벤트로 정리되지는 않는다.

### 원자성과 이벤트 보존

8비트 MCU에서 16비트 공유 변수는 여러 번의 접근으로 처리될 수 있다. 또한 1바이트 변수라도 **읽은 뒤 지우기** 같은 복합 처리는 중간에 ISR이 개입할 수 있다. 임계구역은 필요한 부분만 보호하고, 끝날 때 이전 인터럽트 허용 상태를 복원하는 방식으로 설계한다.

이벤트 비트는 같은 이벤트가 여러 번 발생하면 하나로 합쳐질 수 있다. 발생 횟수가 필요하면 카운터를, 데이터 순서를 보존해야 하면 큐나 링버퍼를 검토한다.

## 7. UART 통신과 상태 추적

USART1은 PC 터미널과 MCU 사이에서 로그와 명령을 주고받는 통로이다. 현재 [uart.c](./DAY2/PM/uart.c)는 **폴링 송신과 인터럽트 수신**을 사용한다.

| 설정·레지스터 | 내용 |
|---|---|
| 클럭 | `F_CPU = 14745600UL` |
| 통신 형식 | 9600 bps, 데이터 8비트, 패리티 없음, 정지 1비트 |
| 흐름 제어 | 없음 |
| `UBRR1H/L` | 보레이트 분주값 |
| `UCSR1A` | 송수신 상태 확인 |
| `UCSR1B` | 송수신과 인터럽트 허용 |
| `UCSR1C` | 프레임 형식 |
| `UDR1` | 송수신 데이터 |

비동기 일반 속도 모드에서 보레이트 설정은 다음 관계로 계산한다.

`UBRR = F_CPU / (16 × baud) - 1`

14.7456 MHz에서 9600 bps를 선택하면 `UBRR = 95`이며, 명목 클럭 기준 분주 오차는 0이다. 실제 통신에는 발진기 오차와 연결 상태도 영향을 준다.

`UDRE1`은 다음 송신 데이터를 쓸 수 있음을 나타내며, `TXC1`의 송신 완료와 구분한다. 수신 ISR은 데이터를 받아 보관하고 메인 루프가 명령을 해석한다. 현재 드라이버의 수신 저장 공간은 한 문자이므로 메인 루프가 처리하기 전에 연속 입력이 들어오면 이전 문자가 덮어써질 수 있다. 링버퍼는 이 한계를 개선하는 확장 학습 주제이다.

## 8. 타이머와 주기 스케줄링

타이머는 입력 클럭을 분주하여 카운트하고, 비교값과 일치하거나 오버플로가 발생하면 이벤트를 만든다. 강의에서는 Timer0 CTC 모드로 기준 tick을 만들고, 소프트웨어 카운터로 여러 실행 주기를 구성한다.

CTC 비교일치 이벤트의 주기는 다음과 같다.

`T_tick = 분주비 × (OCR0 + 1) / F_CPU`

| 항목 | 강의 설정 | 계산 결과 |
|---|---|---|
| CPU 클럭 | 14,745,600 Hz | 보드 기준 클럭 |
| Timer0 분주비 | 1024 | 타이머 클럭 14,400 Hz |
| 비교값 | `OCR0 = 143` | 144카운트마다 비교일치 |
| 기준 tick | 10 ms | 초당 100회 |

| 실행 주기 | tick 수 | 통합 설계의 용도 |
|---|---|---|
| 10 ms | 1 | 버튼 디바운싱 |
| 50 ms | 5 | 센서 샘플링 시작 |
| 250 ms | 25 | LCD 표시 갱신 |
| 1 s | 100 | UART 상태 보고 |

`F_CPU`는 계산에만 쓰는 상수이므로 타이머 주기는 실제 발진 클럭으로만 결정된다. 보드가 바뀌면 가장 먼저 확인할 한 줄이 `F_CPU`이며, 14.7456 MHz는 UART 보레이트에는 정확하지만 1 ms로는 나누어떨어지지 않아 1024 분주로 10 ms를 기준 tick으로 삼는다. 분주만 256으로 바꾸면 같은 `OCR0`으로 2.5 ms가 되어 FND 다중화에 쓴다. 저장소의 [timer.c](./DAY3/AM/timer.c)와 [homework1.c](./DAY3/AM/homework1.c)가 이 tick과 `timer_millis()` 검증을 보여 준다.

### CTC와 Normal, 그리고 공유 레지스터

| 항목 | Normal + `TCNT0` 재적재 | CTC (강의 선택) |
|---|---|---|
| TOP | `0xFF` 고정, ISR에서 `TCNT0 = 112` 또는 `+= 112` | `OCR0` 자체가 TOP |
| 오차 | ISR 진입 지연이 주기마다 누적 | 하드웨어가 비교일치에서 0으로 되돌려 오차 없음 |
| ISR 벡터 | `TIMER0_OVF_vect` | `TIMER0_COMP_vect` |
| 코드 | `TCNT0` 보정이 필요 | `TCNT0`을 건드리지 않음 |

`TIMSK`와 `TIFR`은 Timer0·1·2가 함께 쓰므로 인터럽트 허용은 `|=`로 설정하고, 폴링으로 플래그를 지울 때는 1을 써서 지운다. `sei()` 누락, `OCIE0` 미설정, 잘못된 벡터 이름이 "tick이 오지 않는다"의 대부분이다.

### 수동 부저와 Timer1

이 보드의 부저는 **수동형(passive)** 이라 전압만 걸어서는 울지 않고 구형파를 넣어야 한다. Timer0은 tick, Timer3은 PWM에 쓰이므로 [buzzer.c](./DAY3/AM/buzzer.c)는 비어 있는 **Timer1 CTC**로 약 1,024 Hz 톤을 만든다. `OC1A~OC1C`(PB5~PB7)는 부저 핀(PG3)에 닿지 않아 하드웨어 출력 대신 ISR에서 직접 토글한다. 응용 프로그램은 `buzzer_beep(ms)`로 길이만 정하고 10 ms tick마다 `buzzer_tick()`을 불러 스스로 꺼지게 한다. 음정은 `OCR1A = F_CPU / (2 × 분주 × 주파수) − 1`로 바꾼다.

Super Loop는 이벤트를 확인하고 준비된 작업을 수행한다. 이 구조는 긴 지연 루프를 줄이지만, 개별 작업이 오래 걸리면 다른 작업도 늦어진다(지터). tick 정확도와 응용 작업의 실제 실행 지연을 구분하고, 플래그만 쓸 때 놓친 주기를 어떻게 처리할지도 정해야 한다. 정확한 샘플 시점이나 FND 스캔처럼 지터를 허용할 수 없는 일은 ISR 안에서 처리한다.

## 9. PWM과 LED 밝기 제어

PWM은 일정 주기 안에서 출력이 활성 상태로 유지되는 비율을 바꾸는 방식이다. 주파수는 반복 속도이고, 듀티는 한 주기에서 활성 시간이 차지하는 비율이다.

강의의 보드 연결에 맞는 출력은 **Timer3의 OC3A, PE3에 연결된 D9 LED**이다. Timer0는 기준 tick에 사용하고 Timer3는 PWM에 사용하여 역할을 분리한다.

| 항목 | 강의 설정·의미 |
|---|---|
| 모드 | 8비트 Fast PWM, `WGM33:30 = 0101`, TOP = 255 |
| 분주비 | 64 |
| 주파수 | `14,745,600 / (64 × 256) = 900 Hz` (주기 1.111 ms) |
| 듀티 설정 | `OCR3A` 비교값 0 ~ 255 |
| 출력 극성 | `COM3A1:COM3A0 = 11` 반전 — Active-Low D9는 `OCR3A`가 클수록 밝다 |

주파수와 분해능은 맞바꾸는 관계다. 같은 클럭에서 8비트 TOP은 256단계에 900 Hz, 10비트 TOP은 1024단계에 225 Hz가 된다. LED는 100 Hz 이상이면 깜빡임이 보이지 않고 256단계면 충분하므로 8비트 Fast PWM이 알맞다. 모터처럼 가청 주파수를 피해야 하면 TOP을 자유롭게 정할 수 있는 16비트 타이머가 유리하다.

### 드라이버가 흡수하는 세부

[pwm.c](./DAY3/AM/pwm.c)와 [homework2.c](./DAY3/AM/homework2.c)에서 확인할 점이다.

| 항목 | 처리 |
|---|---|
| 핀 방향 | 타이머는 핀 방향을 자동으로 바꾸지 않는다 — `DDRE`의 `PE3`를 출력으로 두지 않으면 파형이 안 나온다 |
| 듀티 계산 | `percent × 255 / 100`을 `uint8_t`로 곱하면 넘치므로 `uint32_t`로 올려 계산한다 |
| 0 % | 반전 Fast PWM은 `OCR3A = 0`에서도 한 클럭 점등이 남으므로, 완전 소등하려면 비교 출력을 떼고 핀을 HIGH로 만든다 |
| 호흡 효과 | 50 ms tick마다 듀티를 ±5 %; `uint8_t next = duty + step`은 0 아래에서 255가 되므로 `int16_t`로 계산한다 |

16비트 `OCR3A`에 대입할 때 상위·하위 바이트 순서는 컴파일러가 지켜 준다. 직접 나눠 쓰거나 ISR에서 만질 때는 공유 임시 레지스터(TEMP) 때문에 보호가 필요하다.

### OC 핀이 없는 LED — 소프트웨어 PWM

D1~D4(PB0~PB3)는 OC 핀이 아니라 하드웨어 PWM이 닿지 않는다. Timer0의 짧은 tick에서 위상 카운터와 채널별 목표값을 비교해 켜고 끄면 아무 핀에서나 PWM을 흉내 낼 수 있지만, 갱신율이 낮으면 깜빡여 보이고 ISR 부담이 커진다. 하드웨어가 해 줄 수 있으면 하드웨어에 맡긴다.

드라이버는 응용 프로그램의 밝기 요구를 출력 극성에 맞게 변환한다. 사람에게 보이는 밝기는 듀티와 정확히 비례하지 않는다(눈의 로그 응답). 비반전 모드로 바꿔 보면 밝기가 정확히 뒤집힌다.

## 10. ADC와 센서 데이터 처리

ADC는 아날로그 전압을 디지털 코드로 변환한다. 이 과정에서는 가변저항과 조도센서를 읽어 수동 조절값과 자동 조명 판단값으로 사용한다.

| 요소 | 역할·강의 설정 |
|---|---|
| 분해능 | 10비트, 출력 코드 0 ~ 1023 |
| 기준전압 | 보드의 AREF가 AVCC(+5 V)에 묶여 있어 `REFS1:0 = 01` (AVCC) |
| `ADMUX` | 기준전압, 결과 정렬(`ADLAR=0`), 입력 채널(`MUX4:0`) |
| `ADCSRA` | `ADEN` 활성화, `ADSC` 시작, `ADIE` 인터럽트, `ADPS=111` 분주 128 |
| `ADCL/ADCH` | 변환 결과의 하위·상위 바이트 (`ADC` 매크로로 한 번에) |
| `ADC_vect` | 변환 완료 시 데이터 수집 |
| 채널 | VR3 가변저항 = PF0/ADC0, CDS 조도센서 = PF1/ADC1 |

이상적인 양자화 간격은 `V_REF / 1024`이다. 기준전압이 5 V이면 약 4.88 mV이며, 분해능이 곧 측정 정확도를 뜻하지는 않는다. 기준전압의 안정도, 잡음, 온도, 배선의 오차가 함께 작용한다.

### 변환 절차에서 지킬 것

[adc.c](./DAY3/PM/adc.c)와 [homework1.c](./DAY3/PM/homework1.c)에서 확인할 점이다.

| 항목 | 이유 |
|---|---|
| ADC 클럭 50 ~ 200 kHz | 더 빠르면 10비트 정확도를 보장하지 못한다. 분주 128 → 115.2 kHz, 1회 변환 13 클럭 ≈ 112.8 µs |
| 입력 핀 풀업 OFF | `PORTF`의 해당 비트를 0으로. 내부 풀업이 얹히면 측정값이 위로 치우친다 |
| 채널만 교체 | `ADMUX = (ADMUX & 0xE0) \| (ch & 0x1F)` — `REFS0`·`ADLAR`를 보존하는 필드 쓰기 관용구 |
| `ADCL` 먼저 읽기 | `ADCL`을 읽는 순간 `ADCH`가 잠긴다. `ADCH`를 먼저 읽으면 값이 섞인다 (`ADC` 매크로가 순서를 지킴) |
| 겹쳐 시작 금지 | 변환 중 플래그를 두고 `adc_start()`가 중복 시작하지 않도록 한다 |

20 Hz 샘플링이면 50 ms 주기 중 변환에 113 µs(0.23 %)만 쓰므로 여유가 크다. 샘플링 주기는 신호의 변화 속도에 맞춘다 — 조도는 10 ~ 20 Hz, 가변저항은 4 Hz면 충분하다.

### 하드웨어 트리거와 자유 실행

`ADATE`를 켜고 `ADTS2:0`으로 트리거 소스를 고르면 소프트웨어 개입 없이 변환이 시작된다. `011`(Timer0 비교일치)은 정확히 10 ms마다, `000`(Free Running)은 끝나자마자 최고 속도로 다시 변환한다. 이 과정은 20 Hz면 충분하고 소프트 트리거가 흐름을 읽기 쉬워 쓰지 않는다. 다채널 Free Running에서 채널을 바꾸면 다음 변환은 이미 시작된 뒤라 한 번은 옛 채널 값이 나오는 함정이 있다.

### 버퍼링과 판정 안정화

| 방법 | 해결하려는 문제 | 고려 사항 |
|---|---|---|
| 최신값 보관 | 가장 최근 측정값을 제어에 전달 | 모든 샘플의 이력은 남지 않는다. |
| 링버퍼 | 생산자와 소비자의 처리 시점 차이 흡수 | 용량과 가득 찼을 때의 정책이 필요하다. |
| 이동평균 | 무작위 잡음 완화 | 구간 `N`이 길수록 응답이 `N/2`만큼 늦어진다. `N`을 2의 거듭제곱으로 두면 나눗셈이 시프트가 된다. |
| 히스테리시스 | 임계값 근처의 반복 상태 전환 억제 | 진입·복귀 임계값을 따로 정한다 (강의: `DARK_ENTER = 380`, `DARK_EXIT = 460`). |

세 방법은 서로 다른 문제를 푼다. 값이 튄다고 무조건 평균을 내면 반응만 느려지고 경계 깜빡임은 그대로다 — 잡음은 이동평균, 판정은 히스테리시스로 나눠 다룬다. 이동평균은 전체를 다시 더하지 않고 `sum -= 나가는 값; sum += 들어오는 값`으로 갱신해 `N`과 무관하게 연산량을 일정하게 유지한다.

조도센서의 ADC 원시값은 별도 보정 없이 물리 단위 lux로 해석할 수 없다. 밝음·어두움 임계값은 실습실 조명에 따라 크게 달라지므로, 먼저 raw 값을 UART로 찍어 보고 정한다. 센서 회로가 반대로 연결되면 밝기와 값의 부호도 반대가 된다.

## 11. Auto Light ECU 통합 설계

최종 학습 목표는 센서 입력으로 조명의 밝기를 결정하고, 버튼으로 모드를 바꾸며, UART로 상태를 확인하는 실습용 ECU이다. MCU는 연산을 수행하는 칩이고, ECU는 센서 입력·출력 회로·소프트웨어를 포함한 제어장치라는 점을 구분한다. 저장소의 [homework2.c](./DAY3/PM/homework2.c)가 구현이다.

| 상태 | 주요 입력 | 제어 동작 |
|---|---|---|
| `ST_AUTO` | 조도센서(CDS) | 히스테리시스로 어둠 판정 후 PWM 듀티 결정 (밝으면 0 %, 어두우면 80 %) |
| `ST_ON` | 없음 | 조도와 무관하게 항상 100 % |
| 공통 | `SW2` 전환 이벤트·타이머 이벤트 | 상태 토글, 표시 갱신, 1초 로그 |

가변저항 `VR3`(ADC0)로 밝기를 직접 정하는 `MANUAL` 상태 추가는 확장 과제로 남아 있다.

### 상태 전이표

| 현재 상태 | 이벤트 | 다음 상태 | 그 상태에서 하는 일 |
|---|---|---|---|
| `ST_AUTO` | `SW2` 눌림 | `ST_ON` | 상태 전환 |
| `ST_AUTO` | CDS 변환 완료 | `ST_AUTO` | 히스테리시스 판정 후 듀티 갱신 |
| `ST_ON` | `SW2` 눌림 | `ST_AUTO` | 상태 전환 |
| `ST_ON` | CDS 변환 완료 | `ST_ON` | 조도와 무관 — 항상 100 % |
| 양쪽 | 1 s 경과 | 유지 | UART 상태 로그 |

상태 기계는 새로운 실행 구조가 아니라 Super Loop 안의 판단 로직을 정리하는 방법이다. 표를 먼저 채우면 빠진 조합이 드러나고, 코드는 표를 옮겨 적는 일이 된다. `INIT`·`ERROR` 상태는 표에 줄만 늘리면 된다.

### 이벤트 루프의 순서

메인 루프는 **① 이벤트 수집 → ② 상태 전이 → ③ 출력 계산 → ④ 표시** 순으로 돈다. `get_events()`는 읽으면서 지우므로 이벤트마다 한 번만 부른다(두 곳에서 부르면 뒤쪽은 놓친다). 표시를 마지막에 두어 이번 바퀴의 최종 결과만 보이게 한다. 루프 한 바퀴는 수십 µs이고, 이 값이 곧 시스템의 응답 시간이 된다.

### 한 조각씩 붙인다

| 단계 | 붙이는 것 | 확인 방법 |
|---|---|---|
| 1 | timer + uart | 1초마다 로그가 정확히 나온다 |
| 2 | + adc | raw 값이 조도에 따라 움직인다 |
| 3 | + 이동평균 | 값이 안정된다 (로그로 비교) |
| 4 | + pwm | 듀티를 수동으로 넣어 밝기가 바뀐다 |
| 5 | + btn / FSM | `SW2`로 모드가 바뀐다 |
| 6 | + 히스테리시스 | 경계에서 깜빡이지 않는다 |
| 7 | + lcd | 표시가 UART 값과 일치한다 |

통합은 "조립"이 아니라 "누적"이다. 각 단계마다 빌드 → 다운로드 → 확인 → 폴더 복사로 되돌아갈 지점을 남긴다.

### 통합 시 확인할 항목

| 검증 대상 | 확인 내용 |
|---|---|
| 주기 실행 | 기준 tick과 로그 주기가 설정과 일치하는가 |
| 센서 입력 | 조도와 가변저항 변화가 원시값에 반영되는가 |
| 경계 조건 | 임계값 주변에서 출력이 반복적으로 전환되지 않는가 |
| 모드 전환 | 버튼 이벤트가 중복되거나 유실되지 않는가 |
| 출력 | 듀티 변화와 LED 밝기 방향이 일치하는가 |
| 상태 표시 | LCD·UART가 동일한 시점의 상태와 값을 전달하는가 |
| 응답성 | 표시·로그 처리 중에도 입력과 제어 주기를 만족하는가 |
| 계층 분리 | 응용 로직이 드라이버 API를 통해 장치를 제어하는가 |

계층이 지켜졌는지는 `main`에서 레지스터 이름(`PORTB`·`ADMUX`·`TCCR0`)과 `_delay`를 검색해 한 줄도 나오지 않는지로 확인한다. `sei()`만 예외로, 전체 인터럽트를 켜는 것은 어느 드라이버도 혼자 결정할 수 없으므로 `main`의 책임이다. 이 표는 [DAY3/PM](./DAY3/PM/README.md)의 통합 프로젝트를 검증하는 기준이다.

## 12. 프로젝트 실행과 디버깅

각 실습 폴더의 `.atsln`을 열어 해당 프로젝트를 사용한다. 클럭 정의 `F_CPU=14745600UL`은 드라이버 소스에도 적용되도록 프로젝트 전체 설정에 둔다. 이 매크로는 시간 계산에 사용하는 상수이며, 실제 보드의 발진 주파수를 변경하지 않는다.

| 실습 위치 | 솔루션 | 주요 파일 |
|---|---|---|
| [DAY1/AM](./DAY1/AM/) | `d1am.atsln` | `homework1.c`, `myreg.h`, `myboard.h` |
| [DAY1/PM](./DAY1/PM/) | `d1pm.atsln` | LED·버튼·FND 드라이버와 실습 파일 |
| [DAY2/AM](./DAY2/AM/) | `d2am.atsln` | 외부 인터럽트 실습과 버튼·LED 드라이버 |
| [DAY2/PM](./DAY2/PM/) | `d2pm.atsln` | UART 드라이버, 실습 파일과 `_v2.c` 파일 |
| [DAY3/AM](./DAY3/AM/) | `d3am.atsln` | `timer.c`·`pwm.c`·`buzzer.c` 드라이버와 `homework1~4.c` |
| [DAY3/PM](./DAY3/PM/) | `d3pm.atsln` | `adc.c` 드라이버, 조도 센서 실습과 Auto Light ECU |

**한 번에 빌드할 응용 소스는 하나만 선택한다.** 각 `homework*.c`와 변형 파일에 `main()`이 있을 수 있으므로 함께 링크하면 중복 정의 오류가 발생한다. 필요한 드라이버 조합은 각 실습 폴더의 README를 따른다. `DAY3/AM`의 `fnd.c`·`fnd.h`, `DAY3/PM`의 `clcd.c`·`clcd.h`는 해당 폴더의 어느 실습도 쓰지 않으므로 프로젝트에 넣지 않아도 된다.

### 빌드 결과와 관찰 수단

| 파일·도구 | 확인하는 내용 |
|---|---|
| `.hex` | Flash에 기록할 이미지 |
| `.elf` | 실행 코드와 디버깅 심볼 |
| `.lss` | C 코드와 생성 어셈블리, 최적화 결과 |
| `.map` | 함수·변수 배치와 메모리 사용 |
| I/O View | 주변장치 설정값과 상태 비트 |
| Watch·Memory | 변수, 포인터 대상, 메모리 내용 |
| UART 로그 | 실행을 계속하면서 이벤트와 측정값 관찰 |

빌드 보고서의 정적 SRAM 사용량에는 실행 중 스택 최대 사용량이 포함되지 않는다. 스택 여유가 궁금하면 SRAM을 `0xAA`로 채우고 한참 돌린 뒤 남은 `0xAA` 개수로 최대 사용량을 역산한다. 중단점은 UART 수신과 주기 실행의 시간 관계를 바꿀 수 있으므로 타이밍 문제는 로그와 실제 측정을 함께 사용한다.

### 최적화 수준과 드러나는 결함

| 옵션 | 뜻 | 공유 변수를 루프에서 다시 읽나 | 쓰임 |
|---|---|---|---|
| `-O0` | 최적화 없음 | 매번 읽는다 | Studio 기본값이 아니다 |
| `-O1` | 기본 최적화 | 레지스터에 담아 둔다 | Microchip Studio Debug 기본 |
| `-Os` | 크기 최적화 | 담아 둔다 | Microchip Studio Release 기본 — 실전 |
| `-Og` | 디버깅 친화 | 매번 읽는다 | 단계 실행이 자연스러워 개발 중 권장 |

`-O0`에서만 동작하고 `-O1` 이상에서 깨지면 `volatile` 누락, 초기화되지 않은 변수, 명령 수에 의존하는 타이밍 코드를 의심한다. 최적화는 세 가지 오래된 버그를 드러낸다 — ISR이 바꾸는 변수의 `volatile` 누락(1일차 오전), 16비트 공유 변수의 원자성 무시(2일차 오전), 부호 있는 정수 오버플로 같은 미정의 동작. `-Wall -Wextra`로 대부분 잡히므로 경고 0을 유지한다.

### 코드 리뷰 체크리스트

| 분류 | 확인 |
|---|---|
| 레지스터·계층 | `main`에 레지스터 이름이 없다 · 드라이버가 자기 하드웨어만 안다 · `board.h`로 배선이 모여 있다 |
| 동시성 | ISR 공유 변수에 `volatile`이 있다 · 읽고-지우기가 보호된다 · ISR이 수십 µs 이내로 짧다 |
| 시간 | 블로킹 `_delay`가 없다 · 주기 작업이 tick 기반이다 · `F_CPU`가 실제 클럭과 같다 |
| 빌드·품질 | `-Wall -Wextra`에서 경고 0 · `-O0`과 `-Os` 모두에서 동작 · `.map`에서 SRAM 여유 충분 |
| 검증 | 검증 항목표를 만들었다 · 가장 밝음·가장 어두움의 경계 조건을 시험했다 · 오래 돌려도 값이 무너지지 않는다 |
